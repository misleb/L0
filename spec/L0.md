# The L0 Programming Language — Specification v1

L0 is a statically typed language compiled to native code through LLVM.
**This document is the complete and only specification of L0.** There is no
other documentation. Code that relies on syntax or behavior not described here
is invalid, even if it happens to work.

Self-compilation is the goal that shaped this document. Every rule in v1 exists
because it served that goal, and the language must still be able to compile
itself — that is the one property no change may cost. It no longer sets the
direction. L0 is being made general purpose, starting with I/O and memory
management. It is written for agents to read and write, not humans.

L0 is small, and is no longer pure: section 6.2 gives it effects. Smallness is
a description, not a commitment.

## 1. The shape of an L0 program

An L0 program is a set of function and type declarations. One function must be
named `main`, and it is the entry point. It takes one of two forms:

```
(def main ((input (list int))) (list int))    ; a function of the whole input
(def main () int)                             ; a program that streams
```

In the first form, the host reads standard input into a list of byte values,
passes it to `main`, and writes the result to standard output. In the second,
`main` reads and writes as it goes, with the builtins of section 6.2, and its
result is the process's exit status. Section 9 has both in full.

L0 has no mutable state, but it is not pure: the I/O builtins of sections 6.2
to 6.4 are effects in expression position, and the order they happen in is
the evaluation order of section 8. A program that uses none is still a pure
function from bytes to bytes, which is what v1 was, and the compiler is such a
program: its `main` takes L0 source text and returns LLVM IR text.

## 2. Lexical structure

Source text is a sequence of bytes. The following are tokens:

- `(` and `)`
- integer literals
- string literals
- names

Whitespace (space, tab, carriage return, newline) separates tokens and is
otherwise insignificant. A `;` outside a string literal begins a comment that
runs to the end of the line.

### 2.1 Integer literals

An integer literal is an optional `-` followed by one or more decimal digits:
`0`, `7`, `-3`. It must denote a value in the range -9223372036854775808 to
9223372036854775807 inclusive; a literal outside that range is a compile error.

A `-` is part of the literal only when immediately followed by a digit with no
intervening whitespace. `-3` is the integer minus three. `- 3` is an error,
because `-` alone is not a valid name.

### 2.2 String literals

A string literal is a `"`, then zero or more characters, then a closing `"`. It
denotes a value of type `(list int)` holding the byte values of its contents, in
order. `"AB"` is exactly `(cons 65 (cons 66 (nil int)))`.

Inside a string literal, `\` begins an escape. The complete set of escapes is:

- `\n` — byte 10
- `\t` — byte 9
- `\r` — byte 13
- `\\` — byte 92
- `\"` — byte 34
- `\xHH` — the byte with the value of exactly two hexadecimal digits, upper or
  lower case

Any other use of `\` is a compile error. A literal newline byte inside a string
literal is a compile error; use `\n`. Bytes are unsigned: a string literal never
produces a negative element.

### 2.3 Names

There are two kinds of names, distinguished by their first character. This is
what lets a reader tell a constructor from a variable without any context.

- A **lower name** matches `[a-z_][A-Za-z0-9_]*`. Functions, parameters, and
  `let` bindings use lower names.
- An **upper name** matches `[A-Z][A-Za-z0-9_]*`. Data types and their
  constructors use upper names.

These words are reserved and may not be used as any kind of name:

    def   data   if   let   match   nil   true   false   int   bool   list

## 3. Types

A type is one of:

```
type ::= "int"                      ; 64-bit signed integer
       | "bool"                     ; true or false
       | "(" "list" type ")"        ; immutable sequence
       | UpperName                  ; a declared data type
```

`int` is a 64-bit two's-complement signed integer. `add`, `sub`, `mul`, and
`neg` wrap silently on overflow; they never trap.

`(list T)` is an immutable, possibly empty sequence of values of type `T`. `T`
may be any type, including another list or a data type, so `(list (list int))`
is a valid type.

`list` is the only type constructor that takes a parameter. Data types declared
with `data` never take type parameters.

There is no subtyping and no implicit conversion. Two types are equal only if
they are structurally identical.

## 4. Declarations

```
program ::= decl+

decl    ::= "(" "def" lower "(" param* ")" type expr ")"
          | "(" "data" Upper ctor+ ")"

param   ::= "(" lower type ")"
ctor    ::= "(" Upper type* ")"
```

The order of declarations does not matter. Functions may be recursive and may
call each other. Data types may be recursive and may refer to each other.

Every function body is a single expression. There are no statements.

These are compile errors:

- two `def` declarations with the same name
- two `data` declarations with the same name
- two constructors with the same name, even in different data types
- a program type or constructor with a name section 7.1 reserves for the
  prelude
- two parameters of one function with the same name
- a `data` declaration with no constructors
- a reference to a function, type, or constructor that is not declared

A data type is a tagged union of its constructors, each carrying zero or more
fields of fixed types:

```
(data Token
  (TInt int)
  (TName (list int))
  (TLParen)
  (TRParen))
```

`Token` is now a type. `TInt`, `TName`, `TLParen`, and `TRParen` are its four
constructors, and no other data type may reuse those names.

## 5. Expressions

```
expr ::= integer                              ; 3.1
       | string                               ; 3.2
       | "true" | "false"                     ; 3.3
       | lower                                ; variable reference
       | "(" "if" expr expr expr ")"
       | "(" "let" lower expr expr ")"
       | "(" "nil" type ")"
       | "(" "match" expr arm+ ")"
       | "(" Upper expr* ")"                  ; construct a data value
       | "(" lower expr* ")"                  ; call a function or builtin

arm  ::= "(" "(" Upper lower* ")" expr ")"
```

### 5.1 Literals and variables

An integer literal has type `int`. A string literal has type `(list int)`.
`true` and `false` have type `bool`.

A lower name in expression position is a variable reference. It resolves only to
parameters and `let` bindings, never to a function; see section 7.

### 5.2 `if`

```
(if cond then else)
```

`cond` must have type `bool`. There is no truthiness. `then` and `else` must
have the same type, which is the type of the whole expression. Exactly one of
them is evaluated.

### 5.3 `let`

```
(let name value body)
```

`value` is evaluated, bound to `name`, and `body` is evaluated with that binding
in scope. The type of the whole expression is the type of `body`. `name` is not
in scope inside `value`, so `let` cannot define a recursive value.

A `let` binding may shadow a parameter or an enclosing `let` binding of the same
name. Within its body the inner binding wins.

### 5.4 `nil`

```
(nil int)
(nil Token)
(nil (list int))
```

`(nil T)` is the empty list of type `(list T)`. The element type is written
explicitly because L0 has no type inference: every expression's type is
determined by the expression itself and the types of its parts, never by the
context it appears in.

### 5.5 `match`

```
(match subject
  ((TInt n)  (use n))
  ((TName s) (use s))
  ((TLParen) 0)
  ((TRParen) 1))
```

`subject` must have a data type. Each arm names one constructor of that type and
binds one lower name per field of that constructor, in declaration order. The
bindings are in scope in that arm's expression only.

Every arm expression must have the same type, which is the type of the whole
`match`. Exactly one arm is evaluated.

These are compile errors:

- a subject whose type is `int`, `bool`, or a list
- an arm naming a constructor of a different type
- an arm whose name count does not equal the constructor's field count
- the same constructor appearing in two arms
- any constructor of the subject's type not appearing in an arm

A `match` is therefore always exhaustive and never redundant. There is no
wildcard arm and no default arm.

An arm's bindings may shadow outer bindings, following the same rule as `let`.

### 5.6 Construction

```
(TInt 7)
(TLParen)
```

An upper name in expression position constructs a data value. The number of
arguments must equal the constructor's field count, and each argument's type
must equal the declared field type. The result has the constructor's data type.
Nullary constructors are still written with parentheses.

### 5.7 Calls

```
(add 1 2)
(length xs)
```

A lower name in call position resolves to a builtin, or failing that to a `def`.
The number of arguments must equal the declared parameter count, and each
argument's type must equal the corresponding parameter type. The result has the
function's declared return type.

Functions are not values. A function name cannot be passed as an argument,
returned, or bound with `let`. There are no closures and no higher-order
functions.

## 6. Builtins

Every builtin is called like a function. Arities are fixed and there is no
partial application.

| Builtin | Arity | Type | Meaning |
| --- | --- | --- | --- |
| `add` `sub` `mul` | 2 | int, int -> int | arithmetic, wrapping on overflow |
| `neg` | 1 | int -> int | negation, wrapping |
| `div` `mod` | 2 | int, int -> int | see 6.1 |
| `lt` `le` `gt` `ge` | 2 | int, int -> bool | comparison |
| `eq` | 2 | int, int -> bool | equality of integers only |
| `and` `or` | 2 | bool, bool -> bool | strict: both arguments are always evaluated |
| `not` | 1 | bool -> bool | negation |
| `cons` | 2 | T, (list T) -> (list T) | prepend an element |
| `head` | 1 | (list T) -> T | first element; error on the empty list |
| `tail` | 1 | (list T) -> (list T) | all but the first; error on the empty list |
| `is_empty` | 1 | (list T) -> bool | whether the list has no elements |
| `read_byte` | 0 | -> int | the next byte of standard input; see 6.2 |
| `write_byte` | 1 | int -> int | write one byte to standard output; see 6.2 |
| `read_from` | 1 | int -> int | the next byte from a handle; see 6.3 |
| `write_to` | 2 | int, int -> int | write one byte to a handle; see 6.3 |
| `open_read` | 1 | (list int) -> int | open a file for reading; see 6.3 |
| `open_write` | 1 | (list int) -> int | create or truncate a file for writing; see 6.3 |
| `close` | 1 | int -> int | close a handle; see 6.3 |
| `arg_count` | 0 | -> int | how many command-line arguments there are; see 6.4 |
| `arg` | 1 | int -> (list int) | one command-line argument; see 6.4 |

`cons`, `head`, `tail`, and `is_empty` work on any element type. The element
type is determined by the list argument, so no inference is needed: in
`(cons x xs)`, the type of `xs` must be `(list T)` for some `T`, and then `x`
must have type `T`.

`eq` compares integers only. Comparing two lists or two data values is done with
a function written in L0.

`nil` is not a builtin; it is the expression form in section 5.4.

### 6.1 Division

`div` truncates toward zero. `mod` returns the remainder with the sign of the
dividend, so that `(add (mul (div a b) b) (mod a b))` equals `a` whenever `b` is
not zero.

    (div 7 2)    =  3        (mod 7 2)    =  1
    (div -7 2)   = -3        (mod -7 2)   = -1
    (div 7 -2)   = -3        (mod 7 -2)   =  1
    (div -7 -2)  =  3        (mod -7 -2)  = -1

A zero divisor is a runtime error for both.

Dividing the most negative integer by -1 would overflow. It wraps, consistent
with the other arithmetic builtins:

    (div -9223372036854775808 -1)  = -9223372036854775808
    (mod -9223372036854775808 -1)  =  0
    (neg -9223372036854775808)     = -9223372036854775808

### 6.2 Input and output

`(read_byte)` returns the next byte of standard input, in the range 0 to 255,
and waits for one if none has arrived yet. At end of input it returns -1, and
so does every call after that. In a program whose `main` takes its input as a
parameter, standard input has already been read to end of file before `main`
is called, so `read_byte` returns -1 from the start.

`(write_byte b)` writes `b`, reduced modulo 256, to standard output, and
returns 0. Bytes appear in the order the calls are evaluated, which section 8
fixes.

An implementation may hold written bytes back, but only until one of these,
whichever comes first:

- a read, from any handle, that has to wait for input
- the end of the program, whether it returns or fails with a runtime error

So a program that writes a question and then reads the answer always shows the
question before it waits.

Both are effects, so a call's result is not all that matters about it: a
`write_byte` whose result is never used still writes. The way to sequence one
effect before another is `let`, whose value is evaluated before its body:

```
(let w (write_byte 63)       ; "?"
  (read_byte))                ; read only after the question is written
```

### 6.3 Handles and files

A **handle** is an `int` naming an open stream. Three are open from the
start: 0 is standard input, 1 is standard output, and 2 is standard error.
`(read_byte)` is exactly `(read_from 0)`, and `(write_byte b)` is exactly
`(write_to 1 b)`. The rules of 6.2 are the rules for every handle.

A negative result means something went wrong, and says what:

| Result | Meaning |
| --- | --- |
| -1 | end of input, from `read_from` only |
| -2 | not a handle open in that direction |
| -3 | no such file, from `open_read` only |
| -4 | permission denied, from `open_read` and `open_write` |
| -5 | any other failure |

`(open_read path)` opens the file named by the bytes of `path` for reading,
and returns a new handle, or -3, -4, or -5. `(open_write path)` creates the
file, or empties it if it exists, and opens it for writing; it returns a new
handle, or -4 if the file exists and may not be written, or -5.

`(read_from h)` returns the next byte from `h`, as `read_byte` does, -1 at end
of input and every time after, -2 if `h` is not open for reading, or -5 if
reading failed. `(write_to h b)` writes `b`, reduced modulo 256, and returns 0,
or -2 if `h` is not open for writing. A failure to write is reported by
`close`, since bytes may be held back until then.

`(close h)` delivers any bytes held back for `h`, closes it, and returns 0, or
-5 if those bytes could not be written, or -2 if `h` is not open. Handles 0,
1, and 2 cannot be closed: `close` returns -2 for them and they stay open. A
closed handle's number may be reused by a later open.

Output held back for any handle is delivered when the program ends, normally
or with a runtime error, as if every open handle were closed then. Bytes to
handles 1 and 2 are also delivered before any read that has to wait, so a
prompt written to either appears before the program waits. Bytes to different
handles are ordered only within each handle.

The standard library wraps all of this in data types, so that a failure has
to be handled; see `IoOpened` in `lib/io.l0`.

### 6.4 Arguments

`(arg_count)` is the number of command-line arguments the program was given,
not counting the program's own name. `(arg i)` is argument `i`, counted from
0, as a list of its bytes, or the empty list if `i` is negative or not less
than `(arg_count)`. Both always return the same result for the same `i`.

## 7. Name resolution

L0 has three separate namespaces, and which one a name lands in is determined by
its syntactic position, not by what is in scope. This is what makes resolution
unambiguous without any lookahead.

- **Call position** — the first element of a list expression, when it is a lower
  name. Resolves to a builtin first, then to a `def`. Never to a local.
- **Expression position** — a lower name appearing anywhere else. Resolves to a
  parameter or `let` binding. Never to a `def`.
- **Type and constructor position** — upper names. Types resolve against `data`
  declarations, constructors against their constructors.

A consequence worth stating outright: a `let` binding or parameter named `f` does
not interfere with calling a function named `f`, because a local can never appear
in call position and a function can never appear in expression position. Both of
these are legal and unrelated:

```
(def double ((n int)) int (mul n 2))

(def confusing ((double int)) int
  (add double (double 5)))     ; the parameter, then the function
```

Shadowing a builtin name with a `def`, a parameter, or a `let` binding is
allowed. In call position the builtin always wins, so a `def` named `add` can
never be called. This is legal but pointless, and tools may warn about it.

### 7.1 The prelude

A compiler may be given its sources in two groups: a **prelude** and a
**program**. Section 9.1 says how the boundary is conveyed. When there is no
prelude, everything in this subsection is vacuous and the namespaces above are
the whole story.

Function names resolve per group:

- a call in a program declaration resolves to a program function of that name
  if one exists, and otherwise to a prelude function
- a call in a prelude declaration resolves only to prelude functions

A program may therefore define a function the prelude already defines. The
program's definition wins throughout the program, and the prelude goes on
calling its own. This is the only place in L0 where one name denotes two
functions, and it exists for one reason: without it, adding a function to a
prelude breaks every program that had already defined that name.

Two functions with the same name **in the same group** remain an error. A
prelude that calls a function only the program defines is an error too, by the
second rule above: the prelude cannot see the program.

**Type and constructor names are not grouped.** They share one namespace
across both groups, and a duplicate is an error wherever it appears. Two
reasons, both about keeping the checker as simple as it is: a `match` arm
names a constructor without naming its type, so constructor resolution has to
be global for one-level patterns to resolve at all, and a checker that
compares types by name could not tell two same-named types apart.

So that the prelude can gain types without breaking programs, **upper names
that begin with `Io` followed by an uppercase letter are reserved** for it:
`IoFile` and `IoFailed` are reserved, and `Iota` and `Ion` are not. A program
declaration may not declare a type or constructor with a reserved name; a
prelude declaration may. A program may use the prelude's reserved types and
constructors freely.

## 8. Evaluation and errors

L0 is strict and deterministic. Arguments are evaluated left to right, before
the call. `and` and `or` evaluate both arguments; there is no short-circuiting.
`if` and `match` evaluate only the selected branch.

Evaluation order is observable, through `read_byte` and `write_byte` (section
6.2) and through which error is reported first. It is fixed by the rules
above, so that output and failure are both deterministic:

```
(add (div 1 0) (head (nil int)))   ; always reports the division error
(add (write_byte 97) (write_byte 98))   ; always writes "ab"
```

Every `let` value, every argument, and every `and` and `or` operand is
evaluated even when its result is never used, so an effect in any of them
happens. An implementation may still reorder or remove an evaluation that can
neither perform I/O nor fail, since nothing could observe the difference, but
no other.

There are exactly four runtime errors:

- `div` with a zero divisor
- `mod` with a zero divisor
- `head` of the empty list
- `tail` of the empty list

A runtime error writes a one-line diagnostic to standard error and exits with
status 70. Bytes the program already wrote, to any handle, are delivered
first, as 6.3 requires. Nothing else is written to standard output: in a
program whose `main` takes its input, the result is never written. Runtime
errors cannot be caught; L0 has no exception mechanism. A failure of an I/O
builtin is not a runtime error: it is a negative result, which the program
must look at.

A program that type checks cannot read uninitialized memory, call a function
that does not exist, or reach a `match` arm that was never written. The type
checker rules all of those out. Two failures remain possible: exhausting the
stack and exhausting the heap. The host reports both as runtime errors in the
same form.

A program may also fail to terminate. L0 has unrestricted recursion, so
nontermination is possible and is not itself an error. Whether a non-terminating
program runs forever or dies of stack exhaustion depends on whether its
recursion is in tail position and on whether the implementation eliminates tail
calls, so neither outcome is specified.

There are no loops. Iteration is expressed with recursion.

## 9. Programs and the entry point

A complete program is the concatenation of one or more source files. Because
declaration order does not matter and L0 has no module system, splitting a
program across files is purely an editing convenience: the files are joined and
checked as one unit. There are no imports and no visibility modifiers.

The one exception is the prelude of section 7.1, which is a second group of
sources whose function names do not collide with the program's. It is not a
module system: there is still nothing a source file can say about what it
needs or exports, the grouping comes from outside the language, and there are
exactly two groups rather than arbitrarily many.

The program must declare exactly one function named `main`, in one of two
forms. A `main` in the prelude does not satisfy this and is not an entry
point; the prelude is library code, and a program that defines no `main` of
its own has none.

**A function of the whole input.** `main` takes a single parameter of type
`(list int)`, and its return type is one of `(list int)`, `int`, or `bool`.
The host:

1. reads standard input to end of file and builds a `(list int)` of its bytes,
   each in the range 0 to 255, in order
2. evaluates `(main input)`
3. writes the result to standard output, after any bytes `main` wrote with
   `write_byte`, and exits with status 0

How the result is written depends on the return type:

- `(list int)` — each element is written as one byte. Elements are reduced
  modulo 256 to a byte value.
- `int` — written as a decimal integer followed by a newline
- `bool` — written as `true` or `false` followed by a newline

The `int` and `bool` forms exist only so that tests can assert on a scalar
without first writing decimal formatting in L0. A self-hosting L0 compiler
returns `(list int)`.

**A program that streams.** `main` takes no parameters and returns `int`. The
host reads nothing before calling it, so `main` reads standard input itself
with `read_byte` as it needs it. The result is the process's exit status,
reduced modulo 256 to the range 0 to 255, and nothing is written on `main`'s
behalf.

```
(def echo () int
  (let b (read_byte)
    (if (lt b 0)
        0
        (let w (write_byte b) (echo)))))

(def main () int
  (echo))
```

### 9.1 Compiler input

An L0 compiler is itself an L0 program, so it reads its source as bytes on one
channel. Plain concatenation loses the file boundaries, and a diagnostic would
then carry a line number in the joined text rather than in the file the reader
has open. The input may begin with a header that restores them:

```
#l0bundle
#prelude 4821
#nomain
0 prelude.l0
4821 util.l0
4900 main.l0
#source
<the concatenated file contents>
```

The header runs from `#l0bundle` to `#source`, and its lines may appear in any
order:

- `<byte offset> <path>` — one per source file, in ascending order of offset.
  A diagnostic is reported against the last file whose offset is at or before
  it, with line and column counted from that file's first byte.
- `#prelude OFFSET` — the source bytes before OFFSET are the prelude and the
  rest are the program, in the sense of section 7.1. OFFSET is the start
  offset of the first program file. Without this line the prelude is empty and
  every declaration belongs to the program.
- `#nomain` — do not require a `main`. This is for checking a fragment, such
  as one library file or a work in progress, and relaxes nothing else: the
  fragment is still type checked in full, and a program `main` that is present
  must still have the signature section 9 requires, and is reported where it
  is declared when it does not.

Input that does not begin with `#l0bundle` is one unnamed source with no
prelude, so piping a single file in still works.

This header is a protocol on the byte channel rather than a language feature.
It is specified here because an L0 compiler must implement it to be usable on
more than one file at a time, not because any of it is visible to an L0
program.

## 10. Compilation target

This section describes what an L0 compiler emits. It is part of the
specification because the L0 compiler must emit exactly this, and because the
runtime it links against is a fixed interface.

### 10.1 Value representation

**Every L0 value is an `i64`.** The type checker has already proved the program
correct, so no type information survives into the generated code.

- `int` — the value itself
- `bool` — 0 for false, 1 for true
- `(list T)` — a pointer to a cons cell, cast to `i64`. The empty list is 0.
- a data type — a pointer to a data block, cast to `i64`

A cons cell is two consecutive `i64` words: the element, then the rest of the
list. A data block is one `i64` tag followed by one `i64` per field. A
constructor's tag is its zero-based position in its `data` declaration. Every
block is allocated large enough for the widest constructor of its type.

Because every value is one word, every function has the same shape of
signature and every local variable is one `i64` slot.

### 10.2 Generated symbols

An L0 function named `f` in the program compiles to `i64 @l0_f_f(i64, ...)`,
with one `i64` parameter per L0 parameter. This applies to `main` as well,
which becomes `@l0_f_main`, with one exception: a `main` with no parameters
still compiles to `i64 @l0_f_main(i64)`, and ignores the argument, so that the
runtime calls every `main` the same way.

A function named `f` in the prelude compiles to `@l0_p_f` instead. The two
prefixes are what allow a prelude and a program to each define `f`, per
section 7.1, and `main` is always a program function so its symbol is
unaffected.

Only `@l0_f_main` and `@l0_main_ret_kind` require external linkage, because
those are the two names the runtime looks up. Every other function may be
emitted with internal linkage, and should be: a program is a closed module, so
internal linkage is what allows the host toolchain to delete the prelude
functions the program never calls.

A compiled program must also define:

```llvm
@l0_main_ret_kind = global i64 K
```

where K is 0 if `main` takes its input and returns `int`, 1 if `bool`, 2 if
`(list int)`, and 3 if `main` takes no parameters. The runtime reads it to
decide whether to read the input first, and what to do with the result.

Emitted IR must **not** declare a target triple or data layout. A triple is
derived from the host, and section 10.4 forbids host-derived data from reaching
the output; the same compiler run on two machines must produce the same bytes.
The host toolchain supplies the triple when it assembles the IR.

### 10.3 Runtime interface

The runtime is LLVM IR, linked into every compiled program. It carries no
target triple, for the reason 10.2 gives, and reaches the operating system only
by calling libc. It provides exactly these functions:

```llvm

declare i64 @l0_tail(i64)

```

It also defines the process entry point, which does what section 9 describes
for the form of `main` that `@l0_main_ret_kind` names: reads standard input
first or not, calls `@l0_f_main`, and writes the result or exits with it. It
does so on a thread with a large stack, because every iteration in L0 is
recursion.

Each builtin of sections 6.2 to 6.4 is the runtime call of the same name with
`l0_` in front, taking and returning `i64`. A path is passed as the list it
is, and `@l0_arg` returns a list it builds. The runtime buffers every handle,
and flushes standard output and standard error whenever it is about to wait
for input, and every handle before the process exits, including from a
runtime error, which is what sections 6.2 and 6.3 require.

Every compiled function, in the program and in the prelude alike, calls
`@l0_stack_check` before anything else. It reports stack exhaustion as the
runtime error of section 8 when the stack is nearly used up. The check is
explicit, rather than a handler for the fault that running off the stack
would raise, because catching that fault needs structures and constants that
differ between operating systems, and the runtime has to be the same text on
all of them.

The four builtins that can fail at runtime — `head`, `tail`, `div`, `mod` — are
runtime calls, so generated code contains no error checking at all. The
remaining builtins are plain LLVM instructions: `add`, `sub`, `mul` map to
`add`, `sub`, `mul`; `neg` to `sub i64 0, x`; the comparisons to `icmp slt/sle/
sgt/sge/eq` followed by `zext i1 to i64`; `and`, `or`, `not` to `and`, `or`, and
`xor i64 x, 1`.

`l0_data_new(tag, nfields)` allocates a block with room for `nfields` fields and
returns it. `l0_data_set(block, index, value)` stores a field during
construction. `l0_data_tag` and `l0_data_get` read them back.

Memory is never freed. The runtime allocates from a bump-pointer arena, and
there is no garbage collector. That is safe, since nothing is ever freed early,
but a program's memory is its total allocation, not its live data. A program
that streams can run for as long as its input lasts, so one that allocates for
each byte or line it reads grows without bound. One that reads and writes
bytes without building lists or data values allocates nothing, and runs in
constant memory however much input it sees.

### 10.4 Two implementation freedoms

A compiler may emit whatever internal names, block labels, and instruction
sequences it likes, and it may generate `alloca` slots for locals and let LLVM's
`mem2reg` build SSA rather than constructing `phi` nodes itself. Neither choice
is observable.

A compiler's output must be a deterministic function of its input. Nothing
derived from memory addresses, hash iteration order, the clock, the environment,
or the filesystem may reach the emitted text. Self-compilation is verified by
comparing output bytes, so any nondeterminism breaks the build for reasons that
have nothing to do with correctness.

## 11. Worked examples

The larger of two integers:

```
(def max2 ((a int) (b int)) int
  (if (gt a b) a b))
```

Length, showing recursion over a list:

```
(def length ((xs (list int))) int
  (if (is_empty xs)
      0
      (add 1 (length (tail xs)))))
```

The list `1, 2, ..., n`, showing a helper with an accumulator, `let`, and list
construction. The accumulator is built back-to-front, because `cons` prepends,
so counting `i` down from `n` produces ascending order:

```
(def upto_from ((i int) (acc (list int))) (list int)
  (if (lt i 1)
      acc
      (upto_from (sub i 1) (cons i acc))))

(def upto ((n int)) (list int)
  (let start (nil int)
    (upto_from n start)))
```

Reversing a list, which is the workhorse of the output idiom in section 11.1:

```
(def rev_onto ((xs (list int)) (acc (list int))) (list int)
  (if (is_empty xs)
      acc
      (rev_onto (tail xs) (cons (head xs) acc))))

(def rev ((xs (list int))) (list int)
  (rev_onto xs (nil int)))
```

A data type with `match`, showing that an arm binds one name per field:

```
(data Shape
  (Circle int)
  (Rect int int))

(def area ((s Shape)) int
  (match s
    ((Circle r)   (mul 3 (mul r r)))
    ((Rect w h)   (mul w h))))
```

A recursive data type. `data` declarations may refer to themselves, which is how
trees are built:

```
(data Tree
  (Leaf int)
  (Branch Tree Tree))

(def sum_tree ((t Tree)) int
  (match t
    ((Leaf n)     n)
    ((Branch l r) (add (sum_tree l) (sum_tree r)))))
```

### 11.1 Building output

A program that produces a lot of output must accumulate it in reverse and
reverse once at the end. Appending to the end of a list costs a full copy, so
building output with repeated appends is quadratic in the size of the output and
will appear to hang on large inputs.

The idiom is a function that pushes a chunk onto a reversed accumulator:

```
(def push ((chunk (list int)) (acc (list int))) (list int)
  (if (is_empty chunk)
      acc
      (push (tail chunk) (cons (head chunk) acc))))
```

Each call costs the length of the chunk, not the length of the accumulator, so
total cost is linear in the output. Chunks arrive already in order, and `push`
reverses each one onto the accumulator, so the whole accumulator ends up
backwards and one final `rev` puts it right:

```
(def greet ((input (list int))) (list int)
  (let a (push "hello" (nil int))
    (let b (push ", world" a)
      (let c (push "\n" b)
        (rev c)))))

(def main ((input (list int))) (list int)
  (greet input))
```

This is the single most important performance rule in L0, because the L0
compiler's output is large and every emitted fragment goes through it.

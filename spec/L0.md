# The L0 Programming Language — Specification

L0 is a statically typed language compiled to native code through LLVM.
**This document is the complete and only specification of L0.** There is no
other specification: the standard library's documentation, the examples, and
any guide to writing L0 describe code written in the language, not the
language. Code that relies on syntax or behavior not described here is
invalid, even if it happens to work.

This document describes L0 as it is now. Changes are recorded in the
changelog beside it rather than as numbered versions; "the first version"
below means L0 as it was when it first compiled itself, before it had I/O.

Self-compilation is the goal that shaped this document. Every rule in the
first version exists because it served that goal, and the language must still
be able to compile itself — that is the one property no change may cost. It
no longer sets the
direction. L0 is being made general purpose, starting with I/O and memory
management. It is written for agents to read and write, not humans.

L0 is small, and is no longer pure: section 6.2 gives it effects. Smallness is
a description, not a commitment.

## 1. The shape of an L0 program

An L0 program is a set of function and type declarations. One function must be
named `main`, and it is the entry point. It takes one of two forms:

```
(def main ((input (list int))) (list int))    ; a function of the whole input
(def main () int)                             ; a program that streams
```

In the first form, the host reads standard input into a list of byte values,
passes it to `main`, and writes the result to standard output. In the second,
`main` reads and writes as it goes, with the builtins of section 6.2, and its
result is the process's exit status. Section 9 has both in full.

L0 has no mutable state, but it is not pure: the I/O builtins of sections 6.2
to 6.4 and 6.6, the clock of 6.7, the regions of 6.12 and `board_reset`,
the user mode of 6.13, the interrupts of 6.14, the calls to a kernel of
6.15, the other CPUs of 6.18, and the heap's count of 6.19 are effects in
expression position, and the order they happen in is the evaluation order
of section 8. A program that uses none is still a pure
function from bytes to bytes, which is what the first version was, and the compiler is such a
program: its `main` takes L0 source text and returns LLVM IR text.

## 2. Lexical structure

Source text is a sequence of bytes. The following are tokens:

- `(` and `)`
- integer literals
- float literals
- string literals
- names
- field names

Whitespace (space, tab, carriage return, newline) separates tokens and is
otherwise insignificant. A `;` outside a string literal begins a comment that
runs to the end of the line.

### 2.1 Integer literals

An integer literal is an optional `-` followed by one or more decimal digits:
`0`, `7`, `-3`. It must denote a value in the range -9223372036854775808 to
9223372036854775807 inclusive; a literal outside that range is a compile error.

A `-` is part of the literal only when immediately followed by a digit with no
intervening whitespace. `-3` is the integer minus three. `- 3` is an error,
because `-` alone is not a valid name.

A float literal is an optional `-` followed by one or more decimal digits, a
`.`, and one or more decimal digits: `0.5`, `3.141592653589793`, `-2.0`. It
denotes a `float` (section 3). There is no exponent form. Drop the trailing
zeros of the digits after the point, and let k be how many remain, at most
22. With the point removed, the digits are an integer m, at most 2^53. Then
the literal is m divided by 10^k, which both
being exactly representable makes the correctly rounded value, and its `-`
is `float_neg` applied to it, so `-0.0` is negative zero. A float literal
that does not meet this limit is a compile error naming it; `float_from_bits`
(6.17) writes any other value. `3.141592653589793` meets it, and
`0.1000000000000000055` does not. A `.` that is not between digits is not
part of a literal: `3.` and `.5` are errors.

### 2.2 String literals

A string literal is a `"`, then zero or more characters, then a closing `"`. It
denotes a value of type `(list int)` holding the byte values of its contents, in
order. `"AB"` is exactly `(cons 65 (cons 66 (nil int)))`.

Inside a string literal, `\` begins an escape. The complete set of escapes is:

- `\n` — byte 10
- `\t` — byte 9
- `\r` — byte 13
- `\\` — byte 92
- `\"` — byte 34
- `\xHH` — the byte with the value of exactly two hexadecimal digits, upper or
  lower case

Any other use of `\` is a compile error. A literal newline byte inside a string
literal is a compile error; use `\n`. Bytes are unsigned: a string literal never
produces a negative element.

### 2.3 Names

There are two kinds of names, distinguished by their first character. This is
what lets a reader tell a constructor from a variable without any context.

- A **lower name** matches `[a-z_][A-Za-z0-9_]*`. Functions, parameters, and
  `let` bindings use lower names.
- An **upper name** matches `[A-Z][A-Za-z0-9_]*`. Data types, their type
  parameters, and their constructors use upper names.

These words are reserved and may not be used as any kind of name:

    def   data   if   let   match   nil   true   false   int   bool   list   array

`bytes` and `float` name types (section 3) but are not reserved. Each is a
type only where a type is expected, and may otherwise be the name of a function, parameter,
or binding, since programs had used it as one before it was a type, and
section 7 gives the reason L0 does not take names from programs.

### 2.4 Field names

A **field name** is a `.` immediately followed by a lower name: `.space`,
`.state`. It names a field of a data value (sections 4 and 5.8), and is a
token of its own kind, never a name: a function, parameter, or binding of
the same lower name is unrelated to it, and a program cannot collide with
one. A `.` followed by anything but the first character of a lower name,
outside a float literal, is an error, as it was.

## 3. Types

A type is one of:

```
type ::= "int"                      ; 64-bit signed integer
       | "bool"                     ; true or false
       | "(" "list" type ")"        ; immutable sequence
       | "(" "array" type ")"       ; immutable indexed sequence
       | "bytes"                    ; immutable indexed sequence of bytes
       | "float"                    ; 64-bit IEEE 754 binary floating point
       | UpperName                  ; a declared data type, or a type parameter
       | "(" UpperName type+ ")"    ; a declared data type, given its arguments
       | "(" "fn" "(" type* ")" type ")"   ; a function, as a parameter's type only
```

`int` is a 64-bit two's-complement signed integer. `add`, `sub`, `mul`, and
`neg` wrap silently on overflow; they never trap.

`(list T)` is an immutable, possibly empty sequence of values of type `T`. `T`
may be any type, including another list or a data type, so `(list (list int))`
is a valid type.

`(array T)` is an immutable sequence of values of type `T` of a fixed length,
whose elements are read and replaced by index in constant time; section 6.5.
`T` may be any type, as for a list.

`bytes` is an immutable sequence of bytes, each 0 to 255, of a fixed length,
held one byte per byte and read by index in constant time; section 6.6. It is
how a program holds a large input: a `(list int)` costs a cons cell per byte
and an `(array int)` a word.

`float` is an IEEE 754 binary64 number, with its infinities and NaN; section
6.17. It is a type of its own: no `int` is a `float`, and each conversion is
a builtin.

A data type may take type parameters (section 4). `(Option int)` is the type
`Option` declared with one parameter, given the argument `int`; the arguments
may be any types, so `(Pair (list int) (Option bool))` is valid. A data type
declared without parameters is written as a bare name and never given
arguments. A data type declared with parameters is always given exactly as
many arguments as it has parameters; `Option` alone is not a type.

A bare upper name inside a `data` or `def` declaration that takes type
parameters means the parameter of that name, if there is one. Anywhere else,
and for any other name, it means a declared data type. Within a function
that takes type parameters, each one is a type of its own, equal only to
itself (section 4.1); everywhere else every type is complete.

`(fn (P1 ... Pn) R)` is the type of a function that takes arguments of
types `P1` to `Pn` and returns an `R`. It is written only as the type of a
`def`'s parameter, at the top of that type, and nowhere else: not in another
type, a field, a return type, a `nil`, or a construction, so no value of a
function type is ever kept, returned, or built. Section 5.7 says what such
a parameter is given and how it is called. None of `P1` to `Pn` or `R` may
itself be a function type. `fn` is not reserved: it means a function type
only as the first word inside a `(` where a type is expected.

There is no subtyping and no implicit conversion. Two types are equal only if
they are structurally identical: `(Option int)` and `(Option bool)` are
different types, as `(list int)` and `(list bool)` are.

## 4. Declarations

```
program ::= decl+

decl    ::= "(" "def" lower "(" param* ")" type expr ")"
          | "(" "def" "(" lower Upper+ ")" "(" param* ")" type expr ")"
          | "(" "data" Upper ctor+ ")"
          | "(" "data" "(" Upper Upper+ ")" ctor+ ")"

param   ::= "(" lower type ")"
ctor    ::= "(" Upper type* ")"
          | "(" Upper field+ ")"
field   ::= "(" lower type ")"
```

The order of declarations does not matter. Functions may be recursive and may
call each other. Data types may be recursive and may refer to each other.

Every function body is a single expression. There are no statements.

These are compile errors, where "the same name" means in the same group
when there is a prelude (section 7.1):

- two `def` declarations with the same name
- two `data` declarations with the same name
- two constructors with the same name, even in different data types
- a constructor with more than 31 fields, which is what a block's header can
  describe; see section 10.1
- two parameters of one function with the same name
- two fields of one constructor with the same name
- a constructor that names some of its fields but not all
- two type parameters of one `data` or `def` declaration with the same name
- a type parameter of a `def` that no parameter's type mentions (4.1)
- a `data` declaration with no constructors
- a reference to a function, type, or constructor that is not declared
- a data type given a different number of arguments than it has parameters,
  or a type parameter given any
- a function type anywhere but at the top of a `def` parameter's type
  (section 3), or one of whose parts is a function type

A data type is a tagged union of its constructors, each carrying zero or more
fields of fixed types:

```
(data Token
  (TInt int)
  (TName (list int))
  (TLParen)
  (TRParen))
```

`Token` is now a type. `TInt`, `TName`, `TLParen`, and `TRParen` are its four
constructors, and no other data type may reuse those names.

A constructor may name its fields, each as `(name type)`, so that a program
can read and replace them by name (section 5.8):

```
(data Proc
  (Proc (space int) (ctx (array int)) (state int)))
```

Naming changes nothing else about the constructor: `(Proc 1 c 0)` constructs
a value and `((Proc s c st) ...)` matches one, by position, as for a
constructor whose fields are not named. A constructor names all of its
fields or none, and no two of its fields share a name; two constructors may
use the same field names. A field name is not a name of section 2.3: it
resolves only through a value's type, and a function, parameter, or binding
of the same lower name is unrelated to it.

A data type that takes type parameters names them after its own name:

```
(data (Option T)
  (None)
  (Some T))

(data (Result T E)
  (Ok T)
  (Err E))
```

Each parameter is an upper name, and within the declaration's field types it
stands for whatever type the data type is given in that position: a value of
type `(Option (list int))` built with `Some` holds a `(list int)`. A
parameter's name hides a data type of the same name within the declaration,
and means nothing outside it. A parameter need not appear in any field.

A constructor **determines** a parameter of its type when the parameter
appears in one of that constructor's field types, at any depth. `Some`
determines `T`; `None` determines nothing; `Ok` determines `T` but not `E`.
Section 5.6 says what this decides.

### 4.1 Functions with type parameters

A function may take type parameters too, named after its own name as a data
type's are:

```
(def (rev_onto T) ((xs (list T)) (acc (list T))) (list T)
  (if (is_empty xs)
      acc
      (rev_onto (tail xs) (cons (head xs) acc))))
```

Each is an upper name, in scope in the parameters' types, the return type,
and every type written in the body, in a `nil` or a construction. A
parameter's name hides a data type of the same name within the declaration,
as in a `data` declaration.

Within the declaration a type parameter is a type the function does not
know: a type of its own, equal only to itself. So the body can bind, pass,
and return a value of type `T`, and keep it in lists, arrays, and data
values, but it cannot use it as any particular type. Only a builtin that
takes values of any type accepts it, such as `cons`, `head`, `array_new`, or
`eq`, which compares two values of type `T` (section 6.8), or `compare`,
which orders them (6.11); `lt` does not, and a `match` cannot take it apart,
since it is not a data type. The body is
checked once, and is then correct at every type a call gives it.

Every type parameter must be mentioned by some parameter's type, at any
depth, a function type's (section 3) among them. A call finds what each
stands for from its arguments (section 5.7), so one that no parameter
mentions could never be found, and declaring one is a compile error.

## 5. Expressions

```
expr ::= integer                              ; 5.1
       | string                               ; 5.1
       | "true" | "false"                     ; 5.1
       | lower                                ; variable reference, 5.1
       | "(" "if" expr expr expr ")"
       | "(" "if" (expr expr)+ expr ")"         ; a chain of tests, 5.2
       | "(" "let" lower expr expr ")"
       | "(" "let" "(" (lower expr)+ ")" expr ")"   ; several bindings, 5.3
       | "(" "nil" type ")"
       | "(" "match" expr arm+ ")"
       | "(" Upper expr* ")"                  ; construct a data value, 5.6
       | "(" "(" Upper type+ ")" expr* ")"    ; the same, its type written, 5.6
       | "(" lower expr* ")"                  ; call a function or builtin
       | "(" field expr ")"                   ; read a field, 5.8
       | "(" field expr expr ")"              ; replace a field, 5.8

arm  ::= "(" "(" Upper lower* ")" expr ")"
```

### 5.1 Literals and variables

An integer literal has type `int`. A string literal has type `(list int)`.
`true` and `false` have type `bool`.

A lower name in expression position is a variable reference. It resolves only to
parameters and `let` bindings, never to a function, but where it is a
function argument (section 5.7); see section 7.

### 5.2 `if`

```
(if cond then else)
(if cond1 then1 cond2 then2 ... else)
```

`cond` must have type `bool`. There is no truthiness. `then` and `else` must
have the same type, which is the type of the whole expression. Exactly one of
them is evaluated.

With more operands, an odd number of them, `(if c1 e1 c2 e2 ... else)` is
exactly `(if c1 e1 (if c2 e2 (... else)))`: the conditions are evaluated in
order until one holds, and the value after it is evaluated, or `else` when
none does. Every `c` must be `bool`, and every `e` and the `else` must have
one type. It means nothing the nesting does not; it is written for a chain
of tests, which `match` has no wildcard for, without the nesting's closing
parens, and everything said of `if` elsewhere, of tail position (section 8)
among it, follows from the nesting. An even number of operands is a compile
error.

### 5.3 `let`

```
(let name value body)
(let (name1 value1 name2 value2 ...) body)
```

`value` is evaluated, bound to `name`, and `body` is evaluated with that binding
in scope. The type of the whole expression is the type of `body`. `name` is not
in scope inside `value`, so `let` cannot define a recursive value.

A `let` binding may shadow a parameter or an enclosing `let` binding of the same
name. Within its body the inner binding wins.

With a parenthesised list of names and values in pairs, `(let (n1 v1 n2 v2
...) body)` is exactly `(let n1 v1 (let n2 v2 (... body)))`: each value is
evaluated in order, with the names before it in scope, so a later value
may use an earlier name, and a `let` of several bindings closes with two
parens rather than one per binding. Everything said of `let` elsewhere
follows from the nesting. A list with no pairs, or with a name and no
value, is a compile error.

### 5.4 `nil`

```
(nil int)
(nil Token)
(nil (list int))
```

`(nil T)` is the empty list of type `(list T)`. The element type is written
explicitly because L0 has no type inference: every expression's type is
determined by the expression itself and the types of its parts, never by the
context it appears in.

### 5.5 `match`

```
(match subject
  ((TInt n)  (use n))
  ((TName s) (use s))
  ((TLParen) 0)
  ((TRParen) 1))
```

`subject` must have a data type. Each arm names one constructor of that type and
binds one lower name per field of that constructor, in declaration order. The
bindings are in scope in that arm's expression only.

Each binding has its field's declared type, with the subject type's arguments
in place of the parameters: matching a subject of type `(Option (list int))`,
the arm `((Some xs) ...)` binds `xs` as a `(list int)`.

Every arm expression must have the same type, which is the type of the whole
`match`. Exactly one arm is evaluated.

These are compile errors:

- a subject whose type is not a data type: `int`, `bool`, `bytes`, a list,
  or an array
- an arm naming a constructor of a different type
- an arm whose name count does not equal the constructor's field count
- the same constructor appearing in two arms
- any constructor of the subject's type not appearing in an arm

A `match` is therefore always exhaustive and never redundant. There is no
wildcard arm and no default arm.

An arm's bindings may shadow outer bindings, following the same rule as `let`.

### 5.6 Construction

```
(TInt 7)
(TLParen)
```

An upper name in expression position constructs a data value. The number of
arguments must equal the constructor's field count, and each argument's type
must equal the declared field type. The result has the constructor's data type.
Nullary constructors are still written with parentheses.

When the data type takes parameters, the type of the result is found from the
arguments, as `cons` finds its type from the list it is given:

```
(Some 5)                        ; (Option int)
(Some (nil bool))               ; (Option (list bool))
((None int))                    ; (Option int)
((Ok int (list int)) 5)         ; (Result int (list int))
((Err int (list int)) "bad")    ; (Result int (list int))
```

In the first form, `(C arg...)`, the constructor must determine every
parameter of its type (section 4). Each argument's type is matched against
its field's declared type, left to right: where the field type has a
parameter the parameter stands for the part of the argument's type in that
position, and elsewhere the two must be equal. A parameter that an earlier
argument has already given a type must be given the same type again. The
result has the data type with the types the parameters stood for.

In the second form, `((C type...) arg...)`, the types are the data type's
arguments, in the order of its parameters, and there must be exactly as many
as it has parameters. Each argument's type must then equal its field's type
with those arguments in place of the parameters, and the result has the data
type with those arguments. This form may be used for any constructor of a
type that takes parameters, and must be used for one that does not determine
every parameter, because then nothing else says what the type is. It may not
be used for a constructor of a type without parameters.

Neither form looks at where the value is used: its type comes from the
expression alone, as section 5.4 requires of every expression.

### 5.7 Calls

```
(add 1 2)
(length xs)
```

A lower name in call position resolves to a `def` the call can see, or failing
that to a builtin (section 7). The number of arguments must equal the declared parameter count, and each
argument's type must equal the corresponding parameter type. The result has the
function's declared return type.

When the function takes type parameters (section 4.1), each argument's type
is matched against its parameter's declared type, left to right, exactly as
a construction's arguments are matched against its fields (5.6): where the
parameter's type has a type parameter, that type parameter stands for the
part of the argument's type in the same position, and elsewhere the two must
be equal. A type parameter that an earlier argument has already given a type
must be given the same type again. The result has the declared return type
with the types the type parameters stood for:

```
(rev_onto "ab" (nil int))                       ; (list int)
(rev_onto (cons true (nil bool)) (nil bool))    ; (list bool)
(rev_onto "ab" (nil bool))                      ; error: argument 2 of rev_onto
                                                ; must be (list int)
```

Every type parameter appears in some parameter's type, so every call
determines them all, and no call writes them. Inside a function with type
parameters, an argument's type may be one of them, and is matched like any
other type: `(rev_onto (tail xs) (cons (head xs) acc))` in the body above
gives `T` the type `T`.

**Functions as arguments.** A parameter whose type is a function type
(section 3) is given a function, by name. The argument in its position must
be a lower name, and is resolved as an expression's name is first: if a
parameter or binding of that name is in scope, the argument is that one,
which must be a parameter of the enclosing `def` whose type is a function
type, so a function given to one function can be passed on to another.
Otherwise it names a `def` the call can see, under section 7.1's rules for
a call. A builtin cannot be passed, and neither can anything else: an
expression that is not a name, a `let` or `match` binding, or a parameter
that is not a function, is a compile error there. A function argument
evaluates nothing.

A function's type, as an argument, is `(fn (P1 ... Pn) R)` for the `def`
`(def h ((x1 P1) ... (xn Pn)) R ...)`, and a function parameter's is its
declared type. The arguments of a call are matched against the parameters'
types in two passes: first every argument that is not a function, left to
right, as above; then every function argument, left to right. A function
argument without type parameters is matched like any other, its type
against the parameter's function type, which may give the callee's type
parameters their types, as a list type's element does. A function
argument with type parameters, `(def (h A ...) ...)`, takes them from the
parameter's function type: its parameter types `P1` to `Pn`, with what the
callee's type parameters stand for so far in place of them, must by then
contain none of the callee's type parameters, or the call is a compile
error; `h`'s parameter types are matched against them as a call to `h`
with arguments of those types would be, which finds every type parameter
of `h` (section 4.1), and `h`'s result type, with those in place, is
matched against `R`. So `(sort_by key xs)` may be given a `key` that takes
type parameters, since `xs` has fixed the type `key` takes by then.

```
(def (find_by K T) ((key (fn (T) K)) (k K) (xs (list T))) (Option T)
  (if (is_empty xs)
      ((None T))
      (if (eq (key (head xs)) k) (Some (head xs)) (find_by key k (tail xs)))))

(def name_of ((p Person)) (list int) (match p ((Person n age) n)))

(find_by name_of "ada" people)        ; (Option Person)
```

A call `(f a1 ... an)` whose `f` is a function parameter in scope (section
7) calls the function the parameter was given. Its arguments are matched
against the function type's parameter types, which must equal them, and
the call has the function type's result type. Within the callee, a
function parameter's type mentions the callee's type parameters as any
parameter's type does, and they are types of their own there (section
4.1).

Functions are still not values. A function parameter appears only in call
position or as a function argument, and a name of a `def` only in call
position or as a function argument; anywhere else either is a compile
error. A function cannot be returned, kept in a list or a data value, or
bound with `let`, and there are no closures: a function argument is always
a `def`, which sees nothing but its own arguments, so nothing of the
caller's comes with it. A function that needs more passes it alongside, as
another argument.

### 5.8 Fields

```
(.state p)          ; the state field of p
(.state p -1)       ; p, with -1 as its state field
```

`(.f e)` **reads** field `f` of `e`. `e` must have a data type with exactly
one constructor, and that constructor must name a field `f` (section 4).
The result has the field's declared type, with the type's arguments in
place of its parameters, as a `match` binding has (5.5): for `p` of type
`(Pair int bool)` from `(data (Pair A B) (Pair (first A) (second B)))`,
`(.first p)` is an `int`. `(.f e v)` **replaces** it: the result is `e`
with `v` as field `f`, so `v` must have the field's type, and the result
has `e`'s type. `e` is evaluated, then `v`. Both forms take their type from
the expression alone, as every expression does (5.4): `e`'s type says which
field `f` is, so a field name needs no declaration to resolve against.

These are compile errors:

- a field read or replaced of a value whose type is not a data type, or is
  a type parameter (4.1), which is not known to be one
- of a data type with more than one constructor; `match` takes those apart
- naming a field the constructor does not have, or has by position only
- a replacement whose `v` does not have the field's type
- a field name followed by other than one or two expressions

A replacement is a value, as `array_set`'s result is: `e` is unchanged as
far as any program can tell. Section 6.5's rule decides whether the field is
stored in place. `(.f e v)` consumes `e`, in the sense of 10.3, and when
nothing else holds it the field is stored into its block in constant time;
otherwise the block is copied first, in time proportional to its fields.
Replacing several fields nests, `(.state (.ctx p c) -1)`, and after the
first replacement the value is held by nothing else, so the rest store in
place. As for an array or a map, a read of `e` in a later operand of the
expression that replaces, or a use of `e` after a call that replaces a
field inside it, makes the replacement copy: read first, with `let`, and
replace last. The one read that does not is of the same field, as one
argument of a function whose result replaces it, `(.f r (g ... (.f r)
...))`: section 6.5 takes the field out for `g` and puts the result back,
so an array or map in a record updates in place through a function.

## 6. Builtins

Every builtin is called like a function. Arities are fixed and there is no
partial application.

| Builtin | Arity | Type | Meaning |
| --- | --- | --- | --- |
| `add` `sub` `mul` | 2 | int, int -> int | arithmetic, wrapping on overflow |

`cons`, `head`, `tail`, and `is_empty` work on any element type. The element
type is determined by the list argument, so no inference is needed: in
`(cons x xs)`, the type of `xs` must be `(list T)` for some `T`, and then `x`
must have type `T`. The array builtins work the same way: in `(array_new n
x)` the type of `x` determines the element type, and every other array
builtin takes the array first, which determines it.

`eq` compares two values of any one type, which its first argument
determines, as `cons`'s list does: section 6.8. `hash` takes a value of any
type: section 6.9. `compare` orders two values of any one type, as `eq`
takes them: section 6.11. `lt`, `le`, `gt`, and `ge` compare integers only;
to order anything else, compare it, as in `(lt (compare a b) 0)`.

`nil` is not a builtin; it is the expression form in section 5.4.

### 6.1 Division

`div` truncates toward zero. `mod` returns the remainder with the sign of the
dividend, so that `(add (mul (div a b) b) (mod a b))` equals `a` whenever `b` is
not zero.

    (div 7 2)    =  3        (mod 7 2)    =  1
    (div -7 2)   = -3        (mod -7 2)   = -1
    (div 7 -2)   = -3        (mod 7 -2)   =  1
    (div -7 -2)  =  3        (mod -7 -2)  = -1

A zero divisor is a runtime error for both.

Dividing the most negative integer by -1 would overflow. It wraps, consistent
with the other arithmetic builtins:

    (div -9223372036854775808 -1)  = -9223372036854775808
    (mod -9223372036854775808 -1)  =  0
    (neg -9223372036854775808)     = -9223372036854775808

### 6.2 Input and output

`(read_byte)` returns the next byte of standard input, in the range 0 to 255,
and waits for one if none has arrived yet. At end of input it returns -1, and
so does every call after that. In a program whose `main` takes its input as a
parameter, standard input has already been read to end of file before `main`
is called, so `read_byte` returns -1 from the start.

`(write_byte b)` writes `b`, reduced modulo 256, to standard output, and
returns 0. Bytes appear in the order the calls are evaluated, which section 8
fixes.

An implementation may hold written bytes back, but only until one of these,
whichever comes first:

- a read, from any handle, that has to wait for input
- a `flush` of standard output (section 6.3)
- the end of the program, whether it returns or fails with a runtime error

So a program that writes a question and then reads the answer always shows the
question before it waits.

Both are effects, so a call's result is not all that matters about it: a
`write_byte` whose result is never used still writes. The way to sequence one
effect before another is `let`, whose value is evaluated before its body:

```
(let w (write_byte 63)       ; "?"
  (read_byte))                ; read only after the question is written
```

### 6.3 Handles and files

A **handle** is an `int` naming an open stream. Three are open from the
start: 0 is standard input, 1 is standard output, and 2 is standard error.
`(read_byte)` is exactly `(read_from 0)`, and `(write_byte b)` is exactly
`(write_to 1 b)`. The rules of 6.2 are the rules for every handle, except
that only standard output and standard error are delivered before a read
that has to wait; bytes held back for any other handle wait for its `flush`
or `close`, or the end of the program (below).

They are open even when the host started the program with one of them
closed, but on nothing: a read from it returns -5, and every byte written
to it is lost, a write failure like any other (below). No file the program
opens is ever given 0, 1, or 2, so output meant for one of them never goes
into a file instead. A host with no channel for one of them gives it open on
nothing the same way (section 9.2).

A negative result means something went wrong, and says what:

| Result | Meaning |
| --- | --- |
| -1 | end of input, from `read_from` only |
| -2 | not a handle open in that direction |
| -3 | no such file, from `open_read`, `rename`, and `remove`; from `region_open`, no region the host gives there (6.12) |
| -4 | permission denied, from `open_read`, `open_write`, `open_append`, `rename`, and `remove` |
| -5 | any other failure |
| -6 | no space left where the bytes were going, from `flush` and `close` |
| -7 | the reader of a pipe has gone, from `flush` and `close` |
| -8 | it is a directory, from `open_read`, `open_write`, `open_append`, `rename`, and `remove` |
| -9 | no such directory: the one the file would be in does not exist, from `open_write`, `open_append`, and `rename` |
| -10 | on another file system, from `rename` |

-3 means the host looked for the name and found nothing there: the file,
or a directory on the way to it, does not exist. A name the host cannot
look up, because it is longer than the host allows or its links lead round
in a loop, is not known to be missing, and gives -5. Each of -3 to -10 is
given only where the table says, and only when the host says that is the
reason; when it cannot tell, or the reason is any other, the result is -5.
A host with no files at all gives -3 and -9 as section 9.2 says.

`(open_read path)` opens the file named by the bytes of `path` for reading,
and returns a new handle, or -3, -4, -5, or -8. A directory is not a file
that can be read, so opening one returns -8. `(open_write path)` creates the
file, or empties it if it exists, and opens it for writing; it returns a new
handle, or -4 if the file, or the directory it is to be created in, may not
be written, -8 if it is a directory, -9 if the directory it would be
created in does not exist, or -5.

`(open_append path)` opens the file for writing at its end, creating it
empty if it does not exist, and returns a new handle, or -4, -5, -8, or -9,
as `open_write` does. Nothing already in the file changes.
Bytes written to the handle are added after whatever the file holds when
they are delivered, so bytes another program added meanwhile are kept
rather than overwritten.

`(rename from to)` gives the file named `from` the name `to` instead,
replacing any file already named `to`, and returns 0, or a negative result
with neither name changed: -3 if there is no file named `from`, -4 if
either directory may not be written, -8 if `to` is a directory, -9 if the
directory `to` would be in does not exist, -10 if `to` is on another file
system than `from`, or -5. Renaming a directory onto a file is -5: neither
name is missing, and `to` is not a directory. The replacement is one
step: a program opening `to` finds the old file or the new one, never
neither and never a mixture,
and a program that stops at any point leaves one or the other. That is how a
file is updated safely: write the new contents under another name, check
that `close` returned 0, and rename it over the old. A host cannot rename in
one step between two file systems, which is why that is -10 rather than a
copy. What survives the machine itself losing power is not promised.

`(remove path)` deletes the file named `path` and returns 0, or a negative
result with the file still there: -3 if there is no file by that name, -4 if
it may not be deleted, as when its directory may not be written, -8 if it is
a directory, which is not a file that can be removed and is left as it is,
or -5 if it failed any other way. If `path` names a link, the link is
deleted, and the file it leads to is not. Deleting is one step,
as renaming is: a program that stops at any point leaves the name there or
gone. A handle the program already has open on the file keeps reading or
writing it until it is closed, and the file's bytes go only then; the name
goes at once, so opening it again returns -3, and a new file may be
created by that name.

**Handles in memory.** `(open_bytes s)` returns a new handle open for
reading, whose bytes are the elements of `s` in order, each reduced modulo
256, followed by end of input; or -5 if no handle can be opened.
`(open_buffer)` returns a new handle open for writing that keeps every byte
written to it, or -5. `(buffer_bytes h)` is every byte written to the buffer
`h` since it was opened, in order, or the empty list if `h` is not an open
buffer.

They are handles like any other: `read_from`, `write_to`, `flush`, and
`close` work on them as their direction allows, so code that reads or writes
a handle cannot tell them from a file, and that is how such code is tested
on a string. They never fail once open, and a read from one never has to
wait. A buffer holds nothing back, so `flush` and `close` of it return 0;
closing it discards its bytes, and so does the end of the program.

`(read_from h)` returns the next byte from `h`, as `read_byte` does, -1 at end
of input and every time after, -2 if `h` is not open for reading, or -5 if
reading failed. `(write_to h b)` writes `b`, reduced modulo 256, and returns 0,
or -2 if `h` is not open for writing. A failure to write is reported by
`flush` and `close`, since bytes may be held back until then. Writing to a
pipe whose reader has gone is such a failure: the bytes are lost and the
program carries on, and the host never stops it for that.

`(flush h)` delivers any bytes held back for `h`, leaves it open, and returns
0, or -2 if `h` is not open for writing, or, if any byte written to `h` since
it was opened could not be written, -6 if there was no space for it, -7 if
`h` is a pipe whose reader had gone, or -5. Handles 1 and 2 can be flushed.
A write failure is never forgotten: once a byte written to `h` is lost,
every later `flush` of `h` returns the code of the first byte lost, since
it stays lost whatever succeeds after it.

`(close h)` delivers any bytes held back for `h`, closes it, and returns 0, or
-5, -6, or -7 as `flush` does if any byte written to `h` could not be
written, or -2 if `h` is not open.
Handles 0, 1, and 2 cannot be closed: `close` returns -2 for them, though
they are open, and they stay open; -2 here means "not a handle `close` can
close". A closed handle's number may be reused by a later open.

Output held back for any handle is delivered when the program ends, normally
or with a runtime error, as if every open handle were closed then. Bytes to
handles 1 and 2 are also delivered before any read that has to wait, so a
prompt written to either appears before the program waits. Bytes to different
handles are ordered only within each handle.

A write failure is *reported* when a `flush` or `close` of its handle returns
its code. One that has not been reported when the program ends, including one that
happens while delivering the bytes held back then, is reported by the host
instead, as a runtime error (section 8): the program exits with status 70,
whatever `main` returned, since `main` could not have accounted for a failure
it was never told of. For a `main` that takes its input, writing its result
is writing to handle 1, so a result that cannot be written is such a failure
too. A program that has been told of every failure keeps the status it
returned, so the way to choose the status a failed write exits with is to
`flush` and look.

The standard library wraps all of this in data types, a type of failure for
each kind of operation with only the cases this section lets it give, so
that a failure has to be handled and a case it cannot give does not
compile; `l0 doc IoOpened` shows the one an open returns, and `l0 doc
IoDone` the one renaming, removing, flushing, and closing return.

### 6.4 Arguments

`(arg_count)` is the number of command-line arguments the program was given,
not counting the program's own name. `(arg i)` is argument `i`, counted from
0, as a list of its bytes, or the empty list if `i` is negative or not less
than `(arg_count)`. Both always return the same result for the same `i`. On a
host that gives no arguments, `(arg_count)` is 0 (section 9.2).

### 6.5 Arrays

`(array_new n x)` is an array of `n` elements, each `x`; a negative `n` is a
runtime error. `(array_len a)` is the number of elements of `a`. `(array_get
a i)` is element `i` of `a`, counted from 0, and `(array_set a i x)` is an
array equal to `a` except that element `i` is `x`; for both, an `i` that is
negative or not less than the length is a runtime error.

An array is a value, as a list is: `array_set` returns a new array and `a` is
unchanged, as far as any program can tell.

**Updating in place.** `array_set` consumes its array, in the sense of
section 10.3. When nothing else holds that array — no binding still to be
used, and no field, element, or list — it stores `x` into it and returns it,
in constant time. Otherwise it copies it first, in time proportional to its
length, which is what leaves every other holder's array unchanged. Section
10.3's release rule decides which of these happens, and so a loop that
threads one array through tail calls and keeps no other hold on it updates
in constant time:

```
(def count ((counts (array int))) (array int)
  (let b (read_byte)
    (if (lt b 0)
        counts
        (count (array_set counts b (add (array_get counts b) 1))))))
```

Here `array_get` reads `counts` without holding it, and `array_set` is its
last use, so the count of each byte is updated in place. What decides it,
case by case:

- **a binding used after the `array_set`** still holds the array, so the
  update copies. So does a read of the array nested inside a later operand
  of the same expression: in `(array_set (array_set a 0 x) 1 (array_get a
  2))` the outer `array_get` is a later use of `a`, so the inner
  `array_set` copies. Only operands that are the variable itself are taken
  after the others (10.3); a read inside another operand stays where
  section 8 puts it. Bind the reads with `let` first
- **an array that is a field of a data value** updates in place if the value
  is taken apart by a `match` at its last use, since the match then
  releases the value once it has the fields, and the field's binding is the
  only holder left. If the value is still used after the match, it still
  holds the array, and the update copies. That holds across a call too: in
  `(let t (f s) (g s))`, where `f` takes `s` apart and updates an array or
  map inside it, the caller's `s` is used after the call, so it still
  holds `s`, and `f`'s update copies; bind `(g s)` first
- **an array that is an element of another array** copies, since
  `array_get` gives it a holder of its own while the outer array keeps its
  element, except in exactly this form, where the element goes through a
  function and back into its place:

  ```
  (array_set g y (f a1 ... (array_get g y) ... an))
  ```

  where `array_set` and `array_get` are the builtins (section 7), `g` is
  one variable, `y` is the same variable or the same integer literal both
  times, `f` is any function or builtin called with `(array_get g y)` as
  one of its arguments, and no other of its arguments mentions `g`. It is
  evaluated as written, `(array_get g y)` checking `y` where section 8's
  order puts it among `f`'s arguments, but the element is never given a
  second holder. When `g` has no other holder, the element is taken out of
  `g` for `f`, so that `f`'s argument is its only holder, and `f`'s result
  is put back in its place; nothing can see `g` meanwhile, since no other
  argument mentions it. When `g` has another holder, the element is shared
  as it is written to be, and nothing differs from the plain reading. So a
  table of arrays, each handed to a function that updates it and returns
  it, updates in constant time when written this way, and copies the
  element every time when it is bound by a `let` first or read by another
  argument too. With `f` the builtin `array_set`, this is how a grid kept
  as an array of rows updates a cell in constant time:

  ```
  (array_set g y (array_set (array_get g y) x v))
  ```

  and it applies to an element of any type the program counts (10.3), a
  list, data, or bytes as well as an array, since what is never shared is
  never copied when it is next updated
- **`(array_new n x)` of an array `x`** makes every element the same array,
  so each copies on its first update. An array kept elsewhere, such as in a
  list of earlier versions, copies on its next update

Replacing a field of a data value, `(.f e v)` of section 5.8, consumes `e`
as `array_set` consumes its array, and the cases above decide it the same
way: in place when nothing else holds the value, and after a copy of its
block when something does. A field holding an array, a map, or any other
counted value goes through a function and back in place by the same form
as an array's element:

```
(.f r (g a1 ... (.f r) ... an))
```

where `r` is one variable, `(.f r)` reads the same field `f` the outer form
replaces, `g` is any function or builtin called with `(.f r)` as one of its
arguments, and no other of its arguments mentions `r`. It is evaluated as
written, and when `r` has no other holder, the field is taken out of `r`
for `g`, so that `g`'s argument is its only holder, and `g`'s result is put
back in its place; when `r` has another holder, the field is shared as
written, and nothing differs from the plain reading. So a record whose
array is updated through a function, `(.ctx p (call_result (.ctx p) v))`,
updates the array in place, as `match` taking the record apart did before
fields could say it; nested replacements of other fields around it,
`(.state (.ctx p (call_result (.ctx p) v)) -1)`, keep it so, since the
outer one is given a record held by nothing else.

`array_new` takes time and memory proportional to its length, and a copy
does too.

### 6.6 Bytes

`(read_bytes h)` reads every byte left on the handle `h`, waiting for input
as `read_from` would, and returns them, or empty bytes if `h` is not open for
reading. Its result is bytes, so it has no error code of its own: it leaves
`h` as reading its last byte with `read_from` would, and the next `(read_from
h)` says why it stopped, -1 at the end of the input, or -5 if reading failed,
or -2 if `h` was not open for reading. A program that must not act on part
of its input checks that first. In a program whose `main` takes its input,
standard input has already been read, so `(read_bytes 0)` is empty.

`(read_some h n)` reads the next bytes on `h`, at least one and at most `n`,
and returns them. It waits, as `read_from` would, only while no byte has
arrived, and then returns those that have, without waiting for `n`: on a
terminal or a pipe a read may return fewer than are still to come, so a
program reading a whole stream calls it until it is empty. It returns empty
bytes at the end of the input, if reading failed, or if `h` is not open for
reading, and then the next `(read_from h)` says which, as after `read_bytes`.
An `n` below 1 is a runtime error, before anything is read and whether or
not `h` is open, since empty bytes would read as the end.
So a stream is copied, or checked, in pieces of a size the program chooses,
holding only one piece at a time.

`(bytes_len b)` is the number of bytes in `b`. `(bytes_get b i)` is byte `i`
of `b`, counted from 0, in the range 0 to 255; an `i` that is negative or not
less than the length is a runtime error.

`(bytes_from_list s)` is the elements of `s` as bytes, each reduced modulo
256 as `write_byte` reduces it, and `(bytes_to_list b)` is the bytes of `b`
as a list. String literals are lists (section 2.2), so these are how they
meet bytes: `(bytes_from_list "abc")`.

`(write_bytes h b i j)` writes bytes `i` up to but not including `j` of `b`
to `h`, exactly as that many calls of `write_to` would, and returns 0, or -2
if `h` is not open for writing. Unless 0 ≤ `i` ≤ `j` ≤ `(bytes_len b)`, it is
a runtime error, before anything is written and whether or not `h` is open.

`(bytes_slice b i j)` is bytes `i` up to but not including `j` of `b`, as
bytes of their own, under the same rule as `write_bytes`: unless 0 ≤ `i` ≤
`j` ≤ `(bytes_len b)`, it is a runtime error. `(bytes_concat bs)` is the
bytes of each value in the list `bs`, in order, as one value, empty if `bs`
is. Each copies the bytes it returns once, `j - i` of them or the sum of
the lengths, and neither goes through a list, so a header and a body
become one value, and a value is cut into parts, at the cost of their
bytes alone.

No builtin changes a byte, so bytes are never updated, in place or
otherwise. `eq` tells whether two bytes values hold the same bytes (section
6.8), and `compare` orders them, byte by byte (6.11). A bytes value takes
memory proportional to its length, about one byte per
byte, and `read_bytes` reads into the value it returns, so reading a large
input holds it once; `read_some` holds only the piece it returns.

### 6.7 The clock

`(clock_ns)` is the time on a monotonic clock, in nanoseconds: a count that is
never negative and never decreases while the program runs. Only the
difference between two readings means anything, and it is the real time that
passed between them, so a program times part of itself by reading the clock
before and after it:

```
(let t0 (clock_ns)
  (let b (read_bytes 0)
    (let t1 (clock_ns)
      (sub t1 t0))))        ; nanoseconds spent reading
```

Where the count starts is not promised, and differs between runs and between
machines, so a reading is not a date and is not compared across runs. How
finely it counts, and whether it advances while the machine sleeps, depend on
the host. If the host has no such clock, `(clock_ns)` is -5.

Reading the clock is an effect, as reading input is: it happens where section
8's order puts it among the reads and writes, and it happens even when its
result is never used. It is the only builtin whose result nothing the program
is given determines, so a program that does not read it still gives the same
output for the same input, arguments, and files.

### 6.8 Equality

`(eq a b)` is true when `a` and `b` are the same value, and false otherwise.
`a` may have any type, and `b` must have the same type. Two values are the
same when:

- `int`: they are the same integer
- `bool`: both are `true` or both are `false`
- a list: they have the same length, and their elements are the same at
  each position
- an array: they have the same length, and their elements are the same at
  each index
- `bytes`: they have the same length, and the same byte at each index
- `float`: they have the same key (6.17), so `(eq 0.0 -0.0)` is false, and
  a NaN is the same as itself
- a data type: they were built with the same constructor, and their fields
  are the same at each position

So whether two values are the same depends only on what they hold, never on
how or where they were built: `(eq "ab" (cons 97 "b"))` and `(eq (Some
"x") (Some "x"))` are as true as `(eq 3 3)`, and `(eq (array_new 2 0)
(array_set (array_new 2 0) 1 5))` is false. A function with type parameters
compares its values this way at every type a call gives it.

A data type is compared by its fields, so one whose fields keep something
of how it was built, such as the order its parts arrived in or the unused
slots of a table, is not compared by what it means to the program, and
neither `hash` (6.9) nor `compare` (6.11) is. A type meant to be compared
by what it means keeps its fields a function of that alone, as the
standard library's map does (6.9).

Like every builtin, `eq` evaluates both arguments, left to right, before it
compares them. It stops at the first difference it finds, so it takes time
at most proportional to the smaller of the two values, and however long or
deeply nested they are it needs no more stack than any other call: its only
possible failure is `heap exhausted` (section 8).

`eq` is an equivalence: every value is the same as itself, and if `a` is the
same as `b` it is the same as everything `b` is. `compare` (6.11) orders
values of every type, and agrees with `eq`.

### 6.9 Hashing

`(hash x)` is an integer computed from what `x` holds, for `x` of any type.
It is what a table keyed by values of any type needs: a function with type
parameters can compare two of its values with `eq` (6.8) but cannot look
inside one, and `hash` looks inside for it. It is never negative, so `(mod
(hash x) n)` is a slot from 0 to `n` - 1. The standard library's map is such
a table; `l0 doc Map` shows it. Where each entry lies in its table, and how
large the table is, depend only on which entries it holds, so two maps
holding the same keys, each mapped to the same value, are the same value,
however they were built: `eq` is true of them, their hashes are equal, and
`compare` gives 0, and a map can be a key, an element to sort, or a field
of a value compared with `eq`.

Two values `eq` calls the same have the same hash, whatever their type, and
however they were built: `(hash "ab")` is `(hash (cons 97 "b"))`. Two values
that differ usually have different hashes, but may not, so a table compares
the keys it finds with `eq`.

The hash is defined exactly, and is the same on every host and in every
run, so a program may store one or pin one in a test. A value's **items**
are a sequence of integers, each taken modulo 2^64:

- an `int`: one item, the integer
- a `bool`: one item, 1 for `true` and 0 for `false`
- a `float`: one item, its key (6.17), as an integer
- a list: the items of each element, in order, and then the item 0
- an array: its length, and then the items of each element, in index order
- `bytes`: its length, and then each byte, 0 to 255, in order
- a data value: its constructor's tag, its zero-based position in the
  `data` declaration (10.1); then the items of each field, in order; and
  then the item 0 once for each field the type's widest constructor has
  beyond this one's
- a value of a *word wrapper*, a data type declared without type
  parameters with one constructor of one field of type `int`, `bool`, or
  `float` (10.1): the items of its field, and no tag, since it is that
  word

So the items of `(cons 7 (cons 8 (nil int)))` are 7, 8, 0, and those of
`(Some 5)` are 1, 5, for `(data (Option T) (None) (Some T))`. Then, with
every operation on unsigned 64-bit integers, wrapping, `xor` exclusive or,
and `>>` a shift right that brings in zeros, `bit_xor` and `bit_shr` of 6.10:

```
h = 14695981039346656037
for each item i:   h = (h xor i) * 1099511628211
h = (h xor (h >> 30)) * 13787848793156543929
h = (h xor (h >> 27)) * 10723151780598845931
h = h xor (h >> 31)
(hash x) = h >> 1
```

The first two constants are the 64-bit FNV offset basis and prime, and the
last three steps mix every bit of `h` into the low bits a slot is taken
from. The final shift makes the result a non-negative `int`.

Like `eq`, `hash` evaluates its argument and then reads it without changing
it. It takes time proportional to the size of the value, and however long or
deeply nested the value is it needs no more stack than any other call: its
only possible failure is `heap exhausted` (section 8).

### 6.10 Bits

An `int` is 64 bits, in two's complement (10.1), and these builtins work on
those bits. Bit 0 is the least significant and bit 63 the sign.

`(bit_and a b)`, `(bit_or a b)`, and `(bit_xor a b)` set each bit of the
result from the same bit of `a` and of `b`: 1 if both are 1, if either is,
or if exactly one is.

    (bit_and 12 10)  =  8        (bit_or 12 10)  = 14
    (bit_xor 12 10)  =  6        (bit_and -1 255) = 255

`(bit_xor a -1)` turns every bit of `a` over, so there is no separate bitwise
not.

`(bit_shl a n)` moves every bit of `a` `n` places toward bit 63, bringing in
zeros at bit 0 and losing the bits moved past bit 63; for `n` from 0 to 63
it is `a` times 2 to the `n`, wrapping as `mul` does. `(bit_shr a n)` moves
every bit `n` places toward bit 0, bringing in zeros at bit 63 and losing
the bits moved past bit 0, so its result is never negative once `n` is at
least 1, whatever the sign of `a`. Shifting by 64 or more moves every bit
out, and gives 0, so `(sub (bit_shl 1 n) 1)` is the mask of the lowest `n`
bits for every `n` from 0 to 64. A negative `n` is a runtime error for
both.

    (bit_shl 1 4)    = 16        (bit_shr 256 4)  = 16
    (bit_shl -1 63)  = -9223372036854775808
    (bit_shr -1 60)  = 15        (bit_shr -1 64)  = 0

`(bit_count a)` is how many of the 64 bits of `a` are 1: `(bit_count 255)`
is 8, and `(bit_count -1)` is 64.

There is no shift right that copies the sign bit: `div` by a power of two
divides a negative integer, truncating toward zero as 6.1 says, and no
program here has needed the other rounding. Nor is there a rotation, which
in a 32-bit hash is two shifts and a `bit_or` within a mask.

### 6.11 Ordering

`(compare a b)` is -1 when `a` comes before `b`, 0 when they are the same
value, and 1 when `a` comes after `b`. `a` may have any type, and `b` must
have the same type, as for `eq` (6.8). The order is fixed by what the values
hold:

- `int`: by value, as `lt` orders them, negative before positive
- `bool`: `false` before `true`
- `float`: by key (6.17), which is IEEE 754's total order: negative NaN,
  negative infinity, the negative numbers, -0.0, 0.0, the positive numbers,
  positive infinity, NaN. This is not `float_lt`'s order, which leaves -0.0
  and 0.0 unordered and puts NaN nowhere
- a list, an array, or `bytes`: element by element from the first, and the
  first element that differs decides; if one runs out first, it comes
  first, so `(compare "ab" "abc")` is -1 and `(compare "b" "abc")` is 1. A
  byte is 0 to 255, as `bytes_get` gives it
- a data type: by the constructor's position in its `data` declaration,
  first before later, and for one constructor, field by field from the
  first, each by its own type, as for a list

So `(compare (Some 5) (Some 7))` is -1, and `(None)` comes before every
`(Some x)` for `(data (Option T) (None) (Some T))`. A key built for an order
gets it this way: a value of `(data Rank (Rank int (list int)))` built as
`(Rank (neg count) word)` orders by count, highest first, and then by word.

`compare` agrees with `eq`: it is 0 exactly when `eq` is true. It is a total
order: of two different values one comes first, and if `a` comes before `b`
and `b` before `c`, then `a` comes before `c`. The order is the same on every
host and in every run.

It is the order of what a value holds, not of what the value means to the
program. A number kept as a list of digits from the least significant, say,
is not ordered numerically by it; give such a type a key, or a comparison of
its own.

Like `eq`, `compare` evaluates both arguments, left to right, and then reads
them without changing them. It stops at the first difference, so it takes
time at most proportional to the smaller value, and however long or deeply
nested they are it needs no more stack than any other call: its only
possible failure is `heap exhausted` (section 8).

### 6.12 Regions

A **region** is a range of a machine's device memory that a program reads
and writes itself, as a driver reads and writes a device's registers. It is
how L0 code drives a device. A region is an `int` naming it, as a handle
names a stream, but regions are numbered apart from handles, and neither is
ever the other.

`(region_open base len)` opens a region over the `len` bytes from the
address `base`, and returns it, a number not less than 0, or -3 if the host
gives no region there, or -5 if no more regions can be open. A host gives a
region only over a range that lies wholly within one of its machine's
devices, never over memory the program or the runtime uses: section 9.2
says which hosts give none, and 10.3 which ranges QEMU's virt boards give.
A `len` below 1, or a negative `base`, gives -3. A region stays open until
`region_close` closes it or the program ends, and opening a range twice
gives two regions over the same device. At most 64 regions are open at
once; the 65th gives -5, and each open gives the lowest number no open
region has.

`(region_close r)` closes region `r` and returns 0. `r` is then not a
region, and a later `region_open` may give the same number. Every access
to `r` made before it is complete before the region is gone, as if a
`barrier` came first. It closes no other region, even one over the same
device, and does nothing to the device. A program that keeps a closed
region's number and uses it reaches whatever region has that number now,
or gets `not a region`, as with a handle closed and its number given
again.

`(region_read8 r off)`, `region_read16`, `region_read32`, and
`region_read64` read the 1, 2, 4, or 8 bytes `off` bytes into region `r`,
in one access of exactly that width, and return them as an integer, the
byte at the lowest address least significant: below 64 bits never
negative, so `region_read8` is 0 to 255, and at 64 bits all 64, so
possibly negative. `(region_write8 r off v)`, `region_write16`,
`region_write32`, and `region_write64` write the low 8, 16, 32, or 64 bits
of `v` the same way, in one access, and return 0: `(region_write8 r 0
321)` writes 65.

`(region_read_bytes r off n)` returns a copy of the `n` bytes of region
`r` from `off`, as bytes, and `(region_write_bytes r off b i j)` copies the
bytes of `b` from index `i` up to index `j`, as `write_bytes` takes them
(6.6), into `r` from `off`, and returns 0. They are for a region over
memory, such as pages a kernel shares between processes or gives a
device to read and write, not over a device's registers: each byte is
read or written exactly once, in order of address, lowest first, but in
accesses of whatever widths the host chooses, so no address need be a
multiple of anything. An empty range copies nothing, and its `off` may be
the region's length.

Each of these is a runtime error, raised before anything is read or
written, and checked in this order; the first is `region_close`'s too, so
a region closed twice is caught as an access to a closed one is:

| Order | When | Error |
| --- | --- | --- |
| 1 | `r` is not a region the program has open | `not a region` |
| 2 | of `region_read_bytes`, `n` is negative | `byte count out of range` |
| 2 | of `region_write_bytes`, `i` and `j` are not a range of `b` as `write_bytes` requires | `byte index out of range` |
| 3 | `off` is negative, or the access would end past the region's last byte | `region offset out of range` |
| 4 | the address of an access of one width, the region's `base` plus `off`, is not a multiple of its width | `misaligned region access` |

What a read returns is what the device gives, and what a write does is the
device's to decide: a register may read differently each time, change
because it was read, or ignore what is written to it. That is why each
access is an effect, as I/O is (section 8). It happens exactly once, where
section 8's order puts it, at exactly its width, never merged with another,
split, repeated, or left out because its result goes unused, and accesses
to regions over one device reach it in that order.

`(barrier)` returns 0 once every region access and every access to memory
made before it, a load or a store, is complete, as seen by anything that
could see it, a device included, and before any made after it begins. The
copies `space_read` and `space_write` make (6.13) are such accesses. It is
what a driver puts between writing what a device is to read and telling
the device to read it, and between learning that a device has written
something and reading it. On a host that gives no regions it does nothing
a program can see.

Bytes held back for a handle (6.2, 6.3) are not ordered against region
accesses. On a machine whose serial port is both standard output and a
device a region can be opened over, as the virt boards' are, bytes written
to handle 1 appear after a region write made later unless they were
flushed first.

A region is not the program's memory. No region builtin yields a list,
data, or an array, what `region_read_bytes` returns is bytes copied out,
and what any other read returns is an integer, so nothing read from a
device becomes a value that points anywhere, and no host gives a region
over memory the runtime keeps values in. A region access can
change what a device does, but not any value the program holds, which is
why section 8's guarantee still stands.

```
(def uart_put ((u int) (b int)) int
  (if (eq (bit_and (region_read32 u 24) 32) 32)    ; transmit FIFO full
      (uart_put u b)
      (region_write8 u 0 b)))                       ; the data register

(def main () int
  (let u (region_open 150994944 4096)              ; the PL011, 0x09000000
    (if (lt u 0)
        1
        (let a (uart_put u 104) (uart_put u 105)))))
```

`(board_reset)` restarts the board the program runs on, as if its reset
had been pressed: the program ends, the host's memory and the devices are
as a reset leaves them, and the board's firmware or loader starts again.
It does not return where it restarts the board, and everything the
program wrote to standard output and error is delivered first, as at an
exit. It returns -3 where the host has no board to restart: an operating
system, a process of a kernel, or a board that gives no way to ask. It is
not an exit: it gives no status, and what the board does next is what it
does after any reset, which may be to run the same program again. Section
10.3 says which hosts restart.

### 6.13 User mode

A program can be a kernel: it can run other code as **threads** at user
level, each in an **address space** that holds only the memory the program
maps into it, and get control back each time a thread traps. A thread is
any code, an L0 program built as a process (section 9.2) among it; what it
runs is its own, and what it can reach is only what its space maps. A
space is an `int` naming it, and so is a **frame**, a page of memory the
host keeps apart from the program's own, which the program can map into
spaces but never read or write itself except by copying (below). Spaces and
frames are numbered apart from handles and regions. A space lasts until
`space_free` gives it back, and a frame until `frame_free` does, or until
the program ends.

A **page** is 4096 bytes, and a **user page** is a page-aligned address in
the host's **user range**, which section 10.3 gives for each host with user
mode. A user address is any address in that range.

`(space_new)` makes an empty space and returns it, a number not less than
0, or -5 if the host can make no more, or -3 if the host has no user mode
(section 9.2). `(frame_new)` returns a frame whose 4096 bytes are all 0, a
number not less than 0, or -5 if none is left, or -3 if the host has no
user mode. They are 0 as the CPU sees them: a device that does not reach
frames through the CPU's caches (below) sees them only after a
`frame_sync` with 1 or 3, as it does anything the CPU writes.

`(frame_free_count)` returns how many pages the host has left, not less
than 0, or -3 if the host has no user mode. Frames and the tables
`space_new`, `space_map`, and `space_map_device` take come from the same
pages, so each `frame_new` takes one, and each `frame_free` gives one
back, as do the tables `space_free` gives back; `frame_new` gives -5
only when the count is 0, so a kernel that makes no tables meanwhile can
make that many frames. The count can also grow by itself, where section
10.3 says a host's pages do. A kernel reads it to refuse work the pages
left cannot hold, rather than finding out halfway through.

`(frame_address f)` returns the address at which a device reaches the
4096 bytes of frame `f`, a multiple of 4096 not less than 0, the same for
as long as the frame lasts, or -3 if the host lets no device reach frames.
It is what a driver writes into a device's registers, through a region
(6.12), so that the device reads and writes the frame itself: the same
bytes a thread's mapping reaches and `space_read` and `space_write` copy,
ordered against them by `barrier`. Section 10.3 says what it is on each
host. A frame is never the program's memory, so a device writing one
changes no value the program holds.

`(frame_sync f dir)` makes the bytes of frame `f` agree between the CPU
and a device that reaches the frame at its `frame_address`, and returns
0. With `dir` 1, what the CPU has written to the frame reaches memory, so
that a device about to read the frame reads it. With 2, what the CPU
reads of the frame next comes from memory, so that it is what a device
wrote, and a write of the CPU's to the frame since its last sync with 1
or 3 may be lost. With 3, both, in that order. Every access to the frame
before it is complete before it returns, and none after it begins
before, as `barrier` orders them. On a host whose devices reach frames
through the CPU's caches it changes nothing else; section 10.3 says which
hosts those are. A driver syncs with 1 after writing what a device is to
read and before telling the device, and with 2 after the device says it
has written and before reading, on every host, so that it runs on those
whose devices do not. `f` is checked as `frame_address` checks it, and
then `dir`, which must be 1 to 3.

`(space_map s va f perm)` maps frame `f` at user page `va` of space `s`,
and returns 0, or -5 if the host has no memory left for the tables that
mapping needs, when nothing is mapped. A thread in `s` may then read the frame's bytes at `va` to
`va` plus 4095, and may write them if `perm` has bit 0 set and execute
them if it has bit 1 set: `perm` is 0 to 3. A frame may be mapped at more
than one page, in one space or several, and every mapping reaches the same
bytes.

`(space_map_device s va base len)` maps the device memory holding the
`len` bytes from `base`, page by page, at the user pages from `va` on: the
page holding `base` at `va`, the next at `va` plus 4096, and so on, through
the page holding the range's last byte. A thread in `s` reaches the device
at `va` plus `base`'s offset in its page, as a region over the range would
(6.12), and may read and write the pages, never execute them. It returns 0,
or -3 if the host would give no region over that range: section 6.12 says
which ranges it gives one over, and a `len` below 1 or a negative `base`
gives -3, and -5 is as `space_map`'s. Nothing is mapped when it gives
either, and it decides -3 before
checking any page, after only whether `s` is a space, so a kernel may pass
on what a process asked for without first bounding it.

`(space_unmap s va)` removes the mapping at user page `va` of space `s`,
of a frame or of device memory, whichever builtin made it, and returns 0.
A thread in `s` that then touches the page traps as at a page never
mapped, and the page may be mapped again. The frame is not freed, and the
tables the mapping took stay until `space_free`.

`(space_free s)` removes every mapping of space `s`, gives back the tables
they took, and returns 0, unless a thread of `s` is handed to another CPU
and not yet taken back (6.18). `s` is then not a space, and a later
`space_new` may give the same number, for a space as empty as any new
one. The frames `s` mapped are not freed: each lasts until `frame_free`,
and stays mapped in any other space that maps it.

`(frame_free f)` gives frame `f` back to the host and returns 0. `f` is
then not a frame, and a later `frame_new` may give the same number, its
bytes all 0 again, with the same `frame_address`. A frame mapped in any
space cannot be freed, so no thread is ever left with a page that is gone:
a kernel unmaps it first, or frees the spaces that map it. A device given
a frame's address may still read and write the frame after it is freed,
and only the kernel, which drives the device, can stop it.

A kernel that keeps a number after freeing what it named reaches
whatever is given that number next, or gets `not a space` or `not a
frame`, as section 8's runtime errors say.

`(space_read s va n)` returns a copy of the `n` bytes of `s` from user
address `va`, and `(space_write s va b i j)` copies the bytes of `b` from
index `i` up to index `j`, as `write_bytes` takes them (6.6), into `s`
from `va`, and returns 0. They reach only what `space_map` mapped, whatever
its `perm`: a kernel may write a page its thread may only execute. An empty
range copies nothing and needs nothing mapped.

`(user_run s c)` runs, in space `s`, the thread whose registers the
**context** `c` holds, until the thread next traps, and returns the
context with the registers the thread had then and the trap recorded. A
context is an `(array int)` of the host's context length, laid out as
section 10.3 says for its machine: among its words are the thread's
program counter and stack pointer, the kind of trap, and what the machine
said about it. `user_run` consumes its context, as `array_set` consumes its
array (6.5), so a kernel's loop that hands a context back to it each time
updates it in place. A thread traps when it makes a system call, faults,
or is interrupted by an enabled interrupt (6.14); what a thread's system
call asks is the kernel's to read from its registers and to answer by
setting them before the next `user_run`. A thread that never traps never
returns, unless the kernel set the timer first.

Each of these is a runtime error, raised before anything is mapped,
copied, or run, and checked in this order:

| Order | When | Error |
| --- | --- | --- |
| 1 | `s` is not a space the program has made and not freed | `not a space` |
| 2 | a thread of `s` is handed to another CPU by `cpu_run` and not yet taken back by `cpu_trapped` (6.18), for `space_free` | `space still running` |
| 3 | `f` is not a frame the program has been given and not freed | `not a frame` |
| 4 | `f` is mapped in some space, for `frame_free` | `frame still mapped` |
| 5 | `perm` is not 0 to 3 | `page permissions out of range` |
| 6 | `va` is not a user page, or for `space_map_device` one of the pages it would map is not | `not a user page` |
| 7 | a page it would map is mapped already, by either builtin | `user page already mapped` |
| 8 | the page to unmap is not mapped | `user page not mapped` |
| 9 | `n` is negative | `byte count out of range` |
| 9 | `i` and `j` are not within `b` with `i` not past `j` | `byte index out of range` |
| 10 | a byte to copy is not at a user address, or on no page `space_map` mapped | `user memory not mapped` |
| 11 | `c` is not of the host's context length | `not a context` |

A space is not the program's memory either. Nothing in one becomes a value
the program holds except by `space_read`, which copies, and nothing the
program holds is in one except what `space_write` copies there, so no
thread can reach the program's values, and section 8's guarantee stands
for a kernel as it does for a driver.

```
(def step ((s int) (c (array int))) int
  (let r (user_run s c)
    (if (eq (array_get r 35) 1)               ; an interrupt: end it, run again
        (let d (interrupt_done (array_get r 36)) (step s r))
        (call_number r))))                    ; else the system call's number

(def svc0 () bytes                            ; svc #0, 0xd4000001
  (bytes_from_list (cons 1 (cons 0 (cons 0 (cons 212 (nil int)))))))

(def main () int
  (let s (space_new)
    (let f (frame_new)
      (let m (space_map s 3221225472 f 2)     ; 0xC0000000, readable and executable
        (let w (space_write s 3221225472 (svc0) 0 4)
          (step s (user_context 3221225472 0)))))))
```

The library's `Trap` and `trap_of` say what trap a context records without
reading its words, `call_number`, `call_arg`, and `call_result` read a
system call's number and arguments and give it its result, wherever the
CPU keeps them (6.16), and `user_context` makes a context that starts a
thread at a program counter with a stack pointer.

### 6.14 Interrupts

An **interrupt** is a machine's signal that something happened: a device
needs its driver, or the timer's deadline has passed. Each has a number,
the host's: **0 is the timer's on every host that has interrupts**, and
any other is a device's, as section 10.3 numbers them for each machine.
The program itself is never interrupted. An interrupt reaches it only
where it asks for one, in two ways: `interrupt_wait` waits for one, and an
interrupt while a thread runs (6.13) ends that thread's `user_run`. Either
way the interrupt is **taken**, and stays taken until `interrupt_done`
ends it; until then it is not taken again.

`(timer_at t)` sets the timer's deadline to `t` nanoseconds on the clock
`clock_ns` reads (6.7), and returns 0. Once `(clock_ns)` reaches `t`, the
timer's interrupt is pending, and it stays pending, taken and ended again
and again, until another `timer_at` sets a deadline still to come, or
disarms the timer with a negative `t`. So a kernel sets a new deadline or
disarms the timer before it ends the timer's interrupt. Only one deadline
is set at a time. On a host without interrupts it returns -3.

`(interrupt_enable n)` lets interrupt `n` reach the program, and returns 0,
or -3 if the host has no interrupt `n`. Every interrupt starts disabled,
the timer's too, and none is ever disabled again: one the program no
longer wants, its driver stops the device from raising.

`(interrupt_wait)` waits until an enabled interrupt is pending, takes it,
and returns its number, the lowest first of those pending at once. It
returns -5 at once if none is enabled, since it would wait for ever, and
-3 on a host without interrupts. While a thread runs, an enabled
interrupt that becomes pending ends its `user_run` instead: the context it
returns records an interrupt, and its number, which the host has taken
(10.3), and the thread resumes where it was when it next runs.

`(interrupt_done n)` ends interrupt `n`, and returns 0. It is a runtime
error, before anything is ended, if `n` is not an interrupt the program
has taken and not yet ended: `interrupt not taken`. An interrupt still
pending when it is ended is taken again at the next wait or thread.

An interrupt is an effect, as I/O is, and so is waiting for one; neither
changes a value the program holds, so section 8's guarantee stands.

```
(def slice ((s int) (c (array int))) (array int)     ; 10 ms, then the next
  (let t (timer_at (add (clock_ns) 10000000))
    (user_run s c)))

(def main () int
  (let e (interrupt_enable 0)                         ; the timer
    (let t (timer_at (add (clock_ns) 1000000))        ; 1 ms from now
      (let n (interrupt_wait)                         ; 0, in 1 ms
        (let d (timer_at -1)                          ; disarmed, so not again
          (interrupt_done n))))))
```

### 6.15 Calls to a kernel

A program run as a process of a kernel (section 9.2) reaches the kernel by
system calls. The runtime makes the ones the host interface needs, which
section 10.3 numbers below 256, and a program makes the **kernel's own**,
numbered from 256, with these builtins. What each of the kernel's calls
does, and what its words and bytes mean, is the kernel's to define: a
driver asking for the next bytes sent to it, a client sending some, a
server's reply. L0 fixes only how they are passed.

`(supervisor_call n a b c)` makes the kernel's call `n` with the words
`a`, `b`, and `c`, and returns the word the kernel gives back.
`(supervisor_send n a b i j)` makes call `n` with `a` and the bytes of
`b` from index `i` up to index `j`, as `write_bytes` takes them (6.6),
which the kernel copies out of the process, and returns the kernel's word.
`(supervisor_receive n a max)` makes call `n` with `a` and room for `max`
bytes, which the kernel fills, and returns those it says it wrote: as many
as its word, at most `max`, or none if the word is negative. The kernel
never sees an address of the program's but the one these builtins hand it
for the bytes, and never holds it past the call.

Each of these is a runtime error, raised before the call is made, and
checked in this order:

| Order | When | Error |
| --- | --- | --- |
| 1 | `n` is below 256, a call the runtime keeps for itself | `system call reserved` |
| 2 | for `supervisor_send`, `i` and `j` are not within `b` with `i` not past `j` | `byte index out of range` |
| 2 | for `supervisor_receive`, `max` is negative | `byte count out of range` |

On a host that is not a process of a kernel there is no kernel to call:
`supervisor_call` and `supervisor_send` return -3, and `supervisor_receive`
no bytes. A call is an effect, as I/O is.

```
(def serve ((u int)) int                             ; a serial driver's loop
  (let b (supervisor_receive 257 0 4096)             ; what was sent to it
    (let w (write_all u b 0) (serve u))))

(def send ((s (list int))) int                       ; a client
  (let b (bytes_from_list s)
    (supervisor_send 256 0 b 0 (bytes_len b))))
```

Here `write_all` is the driver's own, writing the bytes to its device's
registers; 256 and 257 are calls the kernel that runs the two defines.

### 6.16 The machine

A program and the IR compiled from it are the same for every host (9.2),
but what a kernel does with a thread is not: how a context lays out its
registers (6.13), which register a system call's number is in, and what
instructions a thread's code is are the CPU's. `(machine)` returns the
number of the CPU the program runs on, so that one program can be a kernel
on each:

| Number | CPU |
| --- | --- |
| 1 | aarch64, 64-bit Arm |
| 2 | riscv64, 64-bit RISC-V |

and 0 where the host does not say, as a host with an operating system does
not. It is the same number every time it is asked, for as long as the
program runs, and asking changes nothing. Section 10.3 says what each
host gives.

```
(def call_instruction () bytes                ; a system call, as the CPU encodes it
  (if (eq (machine) 1)
      (bytes_from_list (cons 1 (cons 0 (cons 0 (cons 212 (nil int))))))    ; svc #0
      (bytes_from_list (nil int))))
```

The library reads a context's registers through it (6.13).

### 6.17 Floating point

A `float` is an IEEE 754 binary64 number: finite values, two zeros, two
infinities, and NaN. Rounding is always to nearest, ties to even, and
nothing in L0 changes it. No float operation is an error of section 8: they
never trap, and give an infinity, a zero, or NaN where IEEE 754 does.

`(float_add a b)`, `(float_sub a b)`, `(float_mul a b)`, and `(float_div a
b)` are IEEE addition, subtraction, multiplication, and division, so
`(float_div 1.0 0.0)` is positive infinity and `(float_div 0.0 0.0)` is NaN,
unlike `div` (6.1). `(float_sqrt a)` is IEEE 754's square root, correctly
rounded: `(float_sqrt -0.0)` is -0.0, `(float_sqrt (float_div 1.0 0.0))` is
positive infinity, and the square root of a number below zero, of negative
infinity, or of NaN is the one NaN below. `(float_neg a)` flips the sign of
`a`, of a zero or NaN too. `(float_lt a b)`, `(float_le a b)`, `(float_gt a b)`, and `(float_ge a
b)` are IEEE's comparisons, true or false by the numbers, so each is false
when either argument is NaN, and `(float_le -0.0 0.0)` is true. There is no
`float_eq`: `eq` (6.8) asks whether two floats are the same value, which is
not whether they are equal numbers.

`(float_from_int n)` is the float nearest `n`, ties to even. `(float_to_int
x)` is `x` truncated toward zero: NaN gives 0, and a value past the range
of `int` gives -9223372036854775808 or 9223372036854775807 by its sign.
`(float_bits x)` is the IEEE 754 bits of `x`, as an `int`, and
`(float_from_bits n)` the float of those bits; each undoes the other, except
that every NaN becomes the NaN below.

**The key.** A `float` is held as its key (10.1): the bits with bits 0 to
62 flipped when the sign bit is set. As a signed integer, keys are in
IEEE 754's totalOrder, and the map is its own inverse. So `eq`, `hash`, and
`compare` (6.8, 6.9, 6.11) work on a float, and on any value holding one,
by the key, with nothing more said: a float can be a key of the library's
map, or an element to sort. They differ from the comparisons above where
IEEE 754 does: `(eq 0.0 -0.0)` is false, `(compare -0.0 0.0)` is -1, and
NaN is `eq` to itself.

**One NaN.** Every NaN an operation gives, and every one `float_from_bits`
gives, has the bits 0x7FF8000000000000, whatever the CPU would have made,
so a program's results do not depend on the host. `float_neg` of it is the
NaN with the sign bit set, 0xFFF8000000000000, the one other NaN, and sorts
before every number. A NaN the program never builds does not exist.

A float is the same on every host and in every run for every operation here,
since each is correctly rounded by IEEE 754, with `float_from_int` and
`float_to_int` as stated.

```
(def radians ((deg int)) float
  (float_div (float_mul (float_from_int deg) 3.141592653589793) 180.0))
```

Absolute value, rounding to an integer value, exponent
literals, and conversion to and from text are not here; a program that needs
one is the reason to add it. The standard library has `float_sin` and
`float_cos`, written in L0 from these builtins; `l0 doc float_sin` says
what they promise.

### 6.18 Other CPUs

A machine may have more than one **CPU**. The program runs on one of
them, CPU 0, and only there: its values, its memory, and everything it
evaluates are that CPU's, as they are on a machine with one. A kernel can
have the others run threads for it (6.13). Another CPU runs only the
threads the program hands it, one at a time, each in its space until it
traps, in the order they were handed, and keeps each that trapped until
the program takes it back. It runs no L0 code. The host numbers the CPUs
it runs threads on from 0, the program's.

`(cpu_count)` returns how many CPUs the host runs threads on, the
program's included, so not less than 1: 1 on a host with no user mode,
on a board run with one CPU, and on a host that starts none of its
others (10.3). It is the same every time it is asked, and asking changes
nothing.

`(cpu_run c s ctx deadline tag)` hands CPU `c` the thread whose context
is `ctx` (6.13), to run in space `s`, and returns 0 at once, before the
thread has run; or -5, handing nothing, when CPU `c` holds as many threads
as it can already, counting those handed and not yet taken back, which is
at least 2 on every host with other CPUs, so that a CPU whose thread
trapped can start the next at once. `cpu_run` copies the context, and
reads `ctx` without consuming it, so the program's array is unchanged
and may be handed to another CPU when one has no room. CPU `c` runs the
thread as `user_run` would, until it traps, or until `clock_ns` (6.7)
reaches `deadline`, by a timer of that CPU's own, not the program's
(6.14); a negative `deadline` sets none. `tag` is any int, the
program's, given back with the thread.

`(cpu_trapped)` takes back the oldest thread not yet taken of the first
CPU, from 1 up, that has one, and returns its context, as `user_run`
would have returned it, followed by two more words: the CPU's number and
the thread's tag. So the library's readers of a context (6.13) read it
as they read `user_run`'s. It returns an empty array at once if no CPU has
a thread to give back: it never waits, so a kernel takes every trap
there is in one pass, and handles them together. A thread whose
deadline came records an interrupt, number 0, the timer's, as one
`user_run` ran would, but that interrupt was taken and ended on its own
CPU: the program does not end it, and holds no interrupt taken because
of it. No other interrupt ends a thread on another CPU: every device's
reaches CPU 0 alone, as section 6.14 says.

`(cpu_wait)` waits as `interrupt_wait` does, until an enabled interrupt is
pending, and takes it and returns its number, or until another CPU has a
thread to give back, and returns -1, at once if one has one already,
taking no interrupt. It returns -5 at once if no interrupt is enabled and
every thread handed to another CPU has been taken back, since it would
wait for ever. On a host with one CPU it is `interrupt_wait`, -3 where
that is. Another CPU's trap reaches it with no interrupt sent between
CPUs that are busy: a host may wake a CPU that has had nothing to do for
a while with an interrupt of its own, which no program enables, takes,
or ends, and which no builtin returns.

Each of these is a runtime error of `cpu_run`, raised before anything is
handed, and checked in this order:

| Order | When | Error |
| --- | --- | --- |
| 1 | `c` is not a CPU from 1 to `(cpu_count)` less 1 | `not a CPU` |
| 2 | `s` is not a space the program has made and not freed | `not a space` |
| 3 | `ctx` is not of the host's context length | `not a context` |

So on a host with one CPU no thread can be handed, and every `cpu_run` is
`not a CPU`.

A space whose thread is handed to another CPU, and not yet taken back,
stays a space the program may use: `space_free` of it is the runtime
error `space still running` (6.13), since the thread may still be
running in it, and everything else is allowed. A page `space_map` maps
there the thread can reach at once; a page `space_unmap` unmaps no
CPU's thread reaches once it returns. `space_read` and `space_write`
copy what memory holds as they copy, which a thread on another CPU may
be writing meanwhile, as two threads that map one frame may, and once
`cpu_trapped` has given a thread back, what it wrote is what they copy.
`user_run` may run a thread in that space on CPU 0 meanwhile, and
`cpu_run` may hand another to any CPU.

Handing a thread over, taking it back, and waiting are effects, as
`user_run` is. No value the program holds is ever on another CPU, since
`cpu_run` copies the context and `cpu_trapped` copies it back, so section
8's guarantee stands.

```
(def collect ((n int)) int                       ; the traps of n threads
  (if (eq n 0)
      0
      (let t (cpu_trapped)
        (if (eq (array_len t) 0)
            (let w (cpu_wait) (collect n))
            (collect (sub n 1))))))

(def both ((s int) (a (array int)) (b (array int))) int   ; on CPUs 1 and 2
  (let x (cpu_run 1 s a -1 7)
    (let y (cpu_run 2 s b -1 8)
      (collect 2))))
```

### 6.19 The heap

Where the host gives the program a heap of its own, of a size fixed when
it is linked (10.3), allocating past it is the runtime error `heap
exhausted` (section 8), which ends the program. `(heap_left)` returns how
many bytes of that heap are free, not less than 0, or -3 where the heap is
an operating system's (9.2), which has no fixed size to run out of short
of the machine's memory. A program reads it to refuse work its heap could
not hold, rather than stopping halfway through, as a kernel reads
`frame_free_count` (6.13) for its frames.

The count is every byte the runtime could give again without asking the
host for more, and every byte the host's heap has free: a value freed is
counted at once, as soon as reference counting frees it (10.3), and a
value made is no longer counted. It is a number of free bytes, not the
largest value that can be made, so it may be more than one allocation
can get when free bytes lie in pieces: a freed cons cell serves another
block of its size at once, but serves a block of another size, or an
array, only once every block near it is freed too. A program that keeps
a reserve of a few megabytes above what it is about to make does not
reach `heap exhausted`. Asking allocates nothing and frees nothing, and
so changes no later count.

```
(def room_for ((n int)) bool                ; n more bytes, and 4 MB to spare
  (let left (heap_left)
    (or (lt left 0) (ge left (add n 4194304)))))
```

## 7. Name resolution

L0 has three separate namespaces, and which one a name lands in is determined by
its syntactic position, not by what is in scope. This is what makes resolution
unambiguous without any lookahead.

- **Call position** — the first element of a list expression, when it is a lower
  name. Resolves to a function parameter (section 5.7) when the innermost
  parameter or binding of that name in scope is one, then to a `def`, then
  to a builtin. Never to any other local.
- **Expression position** — a lower name appearing anywhere else. Resolves to a
  parameter or `let` binding. Never to a `def`.
- **Type and constructor position** — upper names. Types resolve against `data`
  declarations, or within one that takes parameters against its parameters
  first (section 3), and constructors against their constructors. Types and
  constructors are two namespaces, so a type and a constructor may share a
  name, as `(data Box (Box int))` does.
- **Field position** — a field name, `.f` (section 2.4), first in a list
  expression. Resolves against the type of the expression after it
  (section 5.8), never against a declaration or a binding, so field names
  are in no namespace a program's names share.

A consequence worth stating outright: a `let` binding or parameter named `f`,
other than a function parameter, does not interfere with calling a function
named `f`, because such a local can never appear in call position and a
function can never appear in expression position but as a function argument.
Both of these are legal and unrelated:

```
(def double ((n int)) int (mul n 2))

(def confusing ((double int)) int
  (add double (double 5)))     ; the parameter, then the function
```

**A `def` shadows a builtin of the same name.** A call resolves to a builtin
only when no `def` of that name is visible to it, which with a prelude means
visible under the rules of section 7.1. So a program that defines its own
`flush` calls its own everywhere, with its own signature, and anything that
cannot see that `def` still calls the builtin:

```
(def flush ((s (list int))) int (head s))

(def main () int (flush "abc"))     ; 97, from the program's flush
```

This exists for the reason section 7.1 gives for the prelude: without it,
adding a builtin to L0 would take its name from every program that had
already defined it, and the program would fail with a type error in its own
code. Everything the spec says about a builtin by name, such as which
builtins read their arguments without consuming them (section 10.3) and the
nested update of section 6.5, applies only to calls that resolve to the
builtin.

A parameter or `let` binding may also have a builtin's name. It shadows
nothing, since a local is never in call position, unless it is a function
parameter, which shadows a `def` or builtin of its name within its `def`,
where no `let` or `match` binding of the name hides it. No program written
before function types had one, so this changed what no program meant.

### 7.1 The prelude

A compiler may be given its sources in two groups: a **prelude** and a
**program**. Section 9.1 says how the boundary is conveyed. When there is no
prelude, everything in this subsection is vacuous and the namespaces above are
the whole story.

Function names resolve per group:

- a call in a program declaration resolves to a program function of that name
  if one exists, and otherwise to a prelude function
- a call in a prelude declaration resolves only to prelude functions

A program may therefore define a function the prelude already defines. The
program's definition wins throughout the program, and the prelude goes on
calling its own. This and a `def` shadowing a builtin (section 7) are the
only places in L0 where one name denotes two functions, and both exist for
one reason: without them, adding a function to a prelude, or a builtin to
L0, breaks every program that had already defined that name.

Two functions with the same name **in the same group** remain an error. A
prelude that calls a function only the program defines is an error too, by the
second rule above: the prelude cannot see the program.

**Type names and constructor names resolve per group the same way**, for the
same reason, each in its own namespace:

- an upper name in type position in a program declaration is the program's
  type of that name if the program declares one, and otherwise the
  prelude's; in constructor position, in a construction or a `match` arm, it
  is likewise the program's constructor if there is one, and otherwise the
  prelude's
- in a prelude declaration, an upper name is only ever the prelude's

Two types of the same name, one in each group, are different types, and no
value of one is a value of the other. Two types or two constructors with the
same name in the same group remain an error, and a prelude declaration that
names a type or constructor only the program declares refers to one that is
not declared.

A program that declares a type or constructor the prelude also declares
gives up the prelude's, within the program, as it does by defining a
function the prelude defines. It can still hold a value of the prelude's
type, bind it with `let`, and pass it to a prelude function, but it cannot
write the prelude's type in a signature if it declares a type of that name,
and it cannot build or match on the prelude's constructor if it declares a
constructor of that name. Since `match` must name every constructor of the
subject's type, shadowing any one constructor of a prelude type means the
program cannot `match` on that type at all:

```
; prelude
(data Parsed (Ok int) (Bad (list int)))
(def parse ((s (list int))) Parsed (Ok 7))
(def or_zero ((p Parsed)) int (match p ((Ok n) n) ((Bad m) 0)))

; program
(data Reply (Ok (list int)) (Busy))
(def main () int
  (let p (parse "7")
    (match (Ok "yes")               ; the program's Ok, so a Reply
      ((Ok s) (or_zero p))          ; the prelude's Parsed, passed back to it
      ((Busy) 1))))
```

In this program, `(match p ((Ok n) n) ((Bad m) 0))` would be an error, since
its `Ok` is the program's and so is not a constructor of `Parsed`.

## 8. Evaluation and errors

L0 is strict and deterministic. Arguments are evaluated left to right, before
the call, but for the builtins `and` and `or`, which evaluate their first
argument and then their second only when the first does not decide the
result: `(and a b)` evaluates `b` only when `a` is `true`, and is `false`
otherwise, and `(or a b)` evaluates `b` only when `a` is `false`, and is
`true` otherwise. So `(and (not (is_empty xs)) (gt (head xs) 0))` never
takes the head of an empty list. A `def` named `and` or `or` is called as
any `def` is, with both arguments evaluated (section 7).
`if` and `match` evaluate only the selected branch.

Evaluation order is observable, through `read_byte` and `write_byte` (section
6.2), through the clock (section 6.7), through a device's regions (section
6.12), through spaces and the threads run in them (sections 6.13 and
6.18), through
interrupts (section 6.14), through calls to a kernel (section 6.15), and
through which error is reported first. It is fixed by the rules
above, so that output and failure are both deterministic:

```
(add (div 1 0) (head (nil int)))   ; always reports the division error
(add (write_byte 97) (write_byte 98))   ; always writes "ab"
```

Every `let` value, every argument, and the first operand of `and` and
`or` is evaluated even when its result is never used, so an effect in any
of them happens; the second operand of `and` and `or` is evaluated exactly
when the rule above says. An implementation may still reorder or remove an evaluation that can
neither perform I/O, read the clock, access a region or a space, touch an interrupt, call a kernel, nor fail, since nothing
could observe the difference, but no other. Reading a variable is such an evaluation, and section 10.3 fixes
when a compiled program takes a variable's reference, since that decides
what memory it holds.

A builtin can raise exactly twenty-three runtime errors, each with its message:

| Cause | Message |
| --- | --- |
| `div` with a zero divisor | `division by zero` |
| `mod` with a zero divisor | `modulo by zero` |
| `head` of the empty list | `head of empty list` |
| `tail` of the empty list | `tail of empty list` |
| `array_get` or `array_set` with an index out of range | `array index out of range` |
| `array_new` with a negative length | `negative array length` |
| `bytes_get`, `write_bytes`, `bytes_slice`, `region_write_bytes`, `space_write`, or `supervisor_send` with an index out of range | `byte index out of range` |
| `bit_shl` or `bit_shr` by a negative amount | `negative shift` |
| `read_some` with a count below 1, or `region_read_bytes`, `space_read`, or `supervisor_receive` with a negative one | `byte count out of range` |
| a region read, write, or close of a region not open | `not a region` |
| a region read or write past either end of its region | `region offset out of range` |
| a region read or write at an address not a multiple of its width | `misaligned region access` |
| a user-mode builtin given a space the program has not made, or has freed | `not a space` |
| `space_map`, `frame_address`, `frame_sync`, or `frame_free` given a frame the program has not been given, or has freed | `not a frame` |
| `frame_sync` with a `dir` other than 1 to 3 | `sync direction out of range` |
| `frame_free` of a frame mapped in some space | `frame still mapped` |
| `space_map` with a `perm` other than 0 to 3 | `page permissions out of range` |
| mapping or unmapping at an address that is not a user page | `not a user page` |
| mapping at a user page already mapped | `user page already mapped` |
| `space_unmap` of a user page not mapped | `user page not mapped` |
| `space_read` or `space_write` of a byte on no page `space_map` mapped | `user memory not mapped` |
| `user_run` or `cpu_run` with an array not of the host's context length | `not a context` |
| `space_free` of a space whose thread is handed to another CPU and not taken back | `space still running` |
| `cpu_run` to a CPU that is not one of the host's others | `not a CPU` |
| `interrupt_done` of an interrupt not taken, or ended already | `interrupt not taken` |
| a call to a kernel numbered below 256 | `system call reserved` |

The host raises three more, described below: `stack exhausted`, `heap
exhausted`, and `write failed`. No other runtime error exists, except
those of the checks that `L0_RC_CHECK` turns on to find bugs in the
compiler and runtime themselves (section 10.3).

A runtime error writes one line to standard error, `l0: runtime error: `
followed by its message and a newline, and exits with status 70. The
messages are part of this specification, since a test that expects a program
to fail compares them. Bytes the program already wrote, to any handle, are
delivered first, as 6.3 requires. Nothing else is written to standard output: in a
program whose `main` takes its input, the result is never written. Runtime
errors cannot be caught; L0 has no exception mechanism. A failure of an I/O
builtin is not a runtime error: it is a negative result, or for `read_bytes`
and `read_some` empty bytes and then a negative `read_from`, which the
program must look at.

A program that type checks cannot read uninitialized memory, call a function
that does not exist, or reach a `match` arm that was never written. The type
checker rules all of those out. A region (6.12) is not memory the program
holds values in: what a read of one returns is an integer the device gave,
and no region covers the runtime's memory, so this holds of a program that
drives devices too. Two failures remain possible: exhausting the
stack and exhausting the heap. The host reports them as the runtime errors
`stack exhausted` and `heap exhausted`. It reports a write failure the
program was never told of as `write failed`, when the program ends (section
6.3), since that is the one I/O failure a program had no chance to look at.

A program may also fail to terminate. L0 has unrestricted recursion, so
nontermination is possible and is not itself an error.

There are no loops. Iteration is expressed with recursion, and **a tail call
uses no stack**, which is what makes recursion a loop. An expression is in
*tail position* when it is:

- the body of a `def`
- the second or third operand of an `if` in tail position, and for an `if`
  of several tests (5.2), each value and the `else`, as its nesting gives
- the body of a `let` in tail position, of one binding or several (5.3)
- the result of an arm of a `match` in tail position

Nothing else is in tail position: not the condition of an `if`, the value of a
`let`, the subject of a `match`, an argument of a call, a field of a
construction, or an operand of `and` or `or`. A *tail call* is a call in tail
position to a function declared with `def`, a call through a function
parameter (5.7) among them, since what it calls is a `def`; a builtin in
tail position is not one. The activation of a function that makes a tail call ends before the
callee's begins, so a chain of tail calls of any length, between functions of
any arities, needs the stack of one activation. A program whose unbounded
recursion is entirely through tail calls therefore runs until it stops, or
forever, and never exhausts the stack.

Only calls that are not tail calls can exhaust the stack. How deep they can
nest first is not specified, and an implementation may run some of them in
constant stack too.

## 9. Programs and the entry point

A complete program is the concatenation of one or more source files. Because
declaration order does not matter and L0 has no module system, splitting a
program across files is purely an editing convenience: the files are joined and
checked as one unit. There are no imports and no visibility modifiers.

The one exception is the prelude of section 7.1, which is a second group of
sources whose function names do not collide with the program's. It is not a
module system: there is still nothing a source file can say about what it
needs or exports, the grouping comes from outside the language, and there are
exactly two groups rather than arbitrarily many.

The program must declare exactly one function named `main`, in one of two
forms, neither of which takes type parameters. A `main` in the prelude does not satisfy this and is not an entry
point; the prelude is library code, and a program that defines no `main` of
its own has none.

**A function of the whole input.** `main` takes a single parameter of type
`(list int)`, and its return type is one of `(list int)`, `int`, or `bool`.
The host:

1. reads standard input to end of file and builds a `(list int)` of its bytes,
   each in the range 0 to 255, in order
2. evaluates `(main input)`
3. writes the result to standard output, after any bytes `main` wrote with
   `write_byte`, and exits with status 0, or 70 if some output could not be
   written (section 6.3)

How the result is written depends on the return type:

- `(list int)` — each element is written as one byte. Elements are reduced
  modulo 256 to a byte value.
- `int` — written as a decimal integer followed by a newline
- `bool` — written as `true` or `false` followed by a newline

The `int` and `bool` forms exist only so that tests can assert on a scalar
without first writing decimal formatting in L0. A self-hosting L0 compiler
returns `(list int)`.

**A program that streams.** `main` takes no parameters and returns `int`. The
host reads nothing before calling it, so `main` reads standard input itself
with `read_byte` as it needs it. The result is the process's exit status,
reduced modulo 256 to the range 0 to 255, unless a write failure was never
reported to the program (section 6.3), and nothing is written on `main`'s
behalf.

```
(def echo () int
  (let b (read_byte)
    (if (lt b 0)
        0
        (let w (write_byte b) (echo)))))

(def main () int
  (echo))
```

### 9.1 Compiler input

An L0 compiler is itself an L0 program, so it reads its source as bytes on one
channel. Plain concatenation loses the file boundaries, and a diagnostic would
then carry a line number in the joined text rather than in the file the reader
has open. The input may begin with a header that restores them:

```
#l0bundle
#prelude 4821
#nomain
0 prelude.l0
4821 util.l0
4900 main.l0
#source
<the concatenated file contents>
```

The header runs from `#l0bundle` to `#source`, and its lines may appear in any
order:

- `<byte offset> <path>` — one per source file, in ascending order of offset.
  A diagnostic is reported against the last file whose offset is at or before
  it, with line and column counted from that file's first byte.
- `#prelude OFFSET` — the source bytes before OFFSET are the prelude and the
  rest are the program, in the sense of section 7.1. OFFSET is the start
  offset of the first program file. Without this line the prelude is empty and
  every declaration belongs to the program.
- `#nomain` — do not require a `main`. This is for checking a fragment, such
  as one library file or a work in progress, and relaxes nothing else: the
  fragment is still type checked in full, and a program `main` that is present
  must still have the signature section 9 requires, and is reported where it
  is declared when it does not.

Input that does not begin with `#l0bundle` is one unnamed source with no
prelude, so piping a single file in still works.

A compiler may also **warn** of a program that is valid but costs more than
it reads, such as an update that a later use of its variable makes copy
(section 6.5). A warning never makes a program invalid or changes what it
compiles to; this compiler writes each before the IR as an LLVM comment,
`; FILE:LINE:COL: warning: ...`, which the tools show.

This header is a protocol on the byte channel rather than a language feature.
It is specified here because an L0 compiler must implement it to be usable on
more than one file at a time, not because any of it is visible to an L0
program.

### 9.2 Hosts

The **host** is what a compiled program runs on: an operating system, which
the runtime reaches through its C library; a machine with no operating
system, where the runtime is the only code beneath the program; or a kernel
that runs the program as a **process**, unprivileged and in an address
space of its own, which the runtime reaches through system calls (section
10.3). A program and the IR compiled from it are the same for every host,
and a program that must know the CPU beneath it, as a kernel must, asks
`machine` (6.16).

A process's host names no machine. What leaves the process, its streams,
files, arguments, devices, and exit, is a system call the kernel answers,
and everything else, its memory and its clock, is the same on every board
the kernel runs on, so one image of a program runs under any kernel for its
architecture. The kernel decides what each call gives, within what section
6 says it means: it may give a process files, arguments, and devices, or
none, and where it gives none, the process has the absence below.

Every host gives a program what sections 6, 8, and 9 rely on: standard
input, which ends; standard output and standard error; memory and a stack,
whose exhaustion is a runtime error; and a way to stop with an exit status.
How the streams reach the world, and what receives the status, is the
host's to decide. A host may lack only what follows, and then gives what it
says:

| A host may lack | And then | Such hosts |
| --- | --- | --- |
| **A channel for a standard stream** | The stream is open on nothing, as 6.3 says of one the host left closed: a read of standard input returns -5, and a byte written to standard output or error is lost, a write failure like any other. | |
| **A board** | `board_reset` is -3 (6.12). | An operating system and a process of a kernel. |
| **Files** | It is as if the host had a file system with nothing in it, not even a directory, and in which nothing can be made. `open_read`, `rename`, and `remove` return -3, since no file is there, and `open_write` and `open_append` return -9, since there is no directory to make one in. | |
| **Arguments** | `(arg_count)` is 0 (6.4). | |
| **A clock** | `(clock_ns)` is -5 (6.7). | |
| **Devices** | `region_open` is -3 for every range (6.12), and `barrier` still returns 0. | An operating system: a program under one reaches devices through files, and the runtime never asks it for more. |
| **User mode** | `space_new`, `frame_new`, and `frame_free_count` are -3 (6.13), so no space or frame exists: `frame_address` and `frame_free` raise `not a frame`, and every other user-mode builtin `not a space`. | An operating system and a process of a kernel: a program under either runs other code as processes the kernel gives it, not as threads of its own. |
| **Other CPUs** | `(cpu_count)` is 1, `cpu_trapped` is always empty, `cpu_wait` is `interrupt_wait`, and every `cpu_run` raises `not a CPU` (6.18). | A host with no user mode, a board run with one CPU, and one whose host starts none of its others (10.3). |
| **Interrupts** | `timer_at`, `interrupt_enable`, and `interrupt_wait` are -3 (6.14), and since nothing is ever taken, `interrupt_done` raises `interrupt not taken`. | An operating system and a process of a kernel: the kernel beneath takes the machine's interrupts. |
| **A kernel** | `supervisor_call` and `supervisor_send` are -3, and `supervisor_receive` gives no bytes (6.15). | Every host but a process of a kernel. |
| **A heap of its own** | `(heap_left)` is -3 (6.19). | An operating system: the runtime's memory is the C library's, which grows as the system lets it, and `heap exhausted` comes when the system says no. |
| **An environment** | The settings section 10.3 reads from it, `L0_STACK_MB`, `L0_ARRAY_STATS`, and `L0_RC_CHECK`, are as if unset. | |

## 11. Worked examples

The larger of two integers:

```
(def max2 ((a int) (b int)) int
  (if (gt a b) a b))
```

Length, showing recursion over a list:

```
(def length ((xs (list int))) int
  (if (is_empty xs)
      0
      (add 1 (length (tail xs)))))
```

The list `1, 2, ..., n`, showing a helper with an accumulator, `let`, and list
construction. The accumulator is built back-to-front, because `cons` prepends,
so counting `i` down from `n` produces ascending order:

```
(def upto_from ((i int) (acc (list int))) (list int)
  (if (lt i 1)
      acc
      (upto_from (sub i 1) (cons i acc))))

(def upto ((n int)) (list int)
  (let start (nil int)
    (upto_from n start)))
```

Reversing a list, which is the workhorse of the output idiom in section 11.1:

```
(def rev_onto ((xs (list int)) (acc (list int))) (list int)
  (if (is_empty xs)
      acc
      (rev_onto (tail xs) (cons (head xs) acc))))

(def rev ((xs (list int))) (list int)
  (rev_onto xs (nil int)))
```

A data type with `match`, showing that an arm binds one name per field:

```
(data Shape
  (Circle int)
  (Rect int int))

(def area ((s Shape)) int
  (match s
    ((Circle r)   (mul 3 (mul r r)))
    ((Rect w h)   (mul w h))))
```

A recursive data type. `data` declarations may refer to themselves, which is how
trees are built:

```
(data Tree
  (Leaf int)
  (Branch Tree Tree))

(def sum_tree ((t Tree)) int
  (match t
    ((Leaf n)     n)
    ((Branch l r) (add (sum_tree l) (sum_tree r)))))
```

### 11.1 Building output

A program that produces a lot of output must accumulate it in reverse and
reverse once at the end. Appending to the end of a list costs a full copy, so
building output with repeated appends is quadratic in the size of the output and
will appear to hang on large inputs.

The idiom is a function that pushes a chunk onto a reversed accumulator:

```
(def push ((chunk (list int)) (acc (list int))) (list int)
  (if (is_empty chunk)
      acc
      (push (tail chunk) (cons (head chunk) acc))))
```

Each call costs the length of the chunk, not the length of the accumulator, so
total cost is linear in the output. Chunks arrive already in order, and `push`
reverses each one onto the accumulator, so the whole accumulator ends up
backwards and one final `rev` puts it right:

```
(def greet ((input (list int))) (list int)
  (let a (push "hello" (nil int))
    (let b (push ", world" a)
      (let c (push "\n" b)
        (rev c)))))

(def main ((input (list int))) (list int)
  (greet input))
```

This is the single most important performance rule in L0, because the L0
compiler's output is large and every emitted fragment goes through it.
